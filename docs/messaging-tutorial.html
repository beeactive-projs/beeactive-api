MotionHive Messaging

A tutorial and maintenance guide for the messaging feature — backend (NestJS), database (PostgreSQL), and frontend (Angular 21).

v1, 2026-05-13. Covers F1–F8 plus the post-launch audit + fixes. Read top-to-bottom for a complete mental model; jump via the TOC for a specific subsystem.

1 · Overview

Messaging in MotionHive is a 1:1 (direct) instant messenger between any two registered users. It uses Server-Sent Events for live delivery, an in-memory ring buffer for replay across short disconnects, and a deterministic direct_key to make first-send races safe. Group chats are schema-ready but not wired in v1.

Mental model in one paragraph

Two users have at most one DIRECT conversation row. Sending a message goes through three layers: a safety gate (blocks, suspensions, new-account rule, rate limits), a content scan (URLs, payment handles, off-platform contact patterns), and a persistence layer (the message row + a fresh inbox-row snapshot). On commit, an SSE event is fanned out to the other participants AND a stored notification is queued (with the in-app channel suppressed — see notification channel policy).

2 · Stack & technology choices

Backend

  • NestJS 11, TypeScript ES2023
  • Sequelize 6 (sequelize-typescript) on PostgreSQL (Neon)
  • Passport JWT + a dedicated 'messaging-sse' strategy for the SSE endpoint
  • EventEmitter2 for in-process fan-out (Redis Pub/Sub when we scale to multi-instance)
  • Jest 30 + Supertest for unit + integration tests

Frontend

  • Angular 21 standalone components, signal-based state (no NgRx)
  • PrimeNG for Dialog / Toast / Button surfaces
  • Browser EventSource for SSE; JWT delivered via ?token=
  • HttpClient with global error + auth interceptors (refresh-token flow)

2.1 — Why SSE, not WebSockets

SSE was chosen deliberately. The reasoning, in order of weight:

  1. Cost. Long-lived TCP connections behind a managed PaaS (Railway / similar) are billed and limited. SSE multiplexes cleanly over HTTP/2 and survives most reverse proxies without per-connection sticky-session work. WebSockets need explicit sticky routing for fan-out across instances.
  2. Operational simplicity. Browsers handle reconnect natively. The server emits text events; no framing protocol, no ping/pong dance, no upgrade negotiation. The implementation is ~120 lines.
  3. Read-only is enough. We never push writes from the client over the same channel — sends go via POST /messaging/messages. SSE's read-only nature matches the use case.
  4. Auth fit. Tokens live in ?token= on the stream URL (because EventSource can't set headers). We accept the tradeoff because it's a single read-only endpoint and we route the token through a separate Passport strategy (see §8) that's named 'messaging-sse' precisely so it's grep-visible.

2.2 — Why no E2EE in v1

Adding end-to-end encryption would mean: client-side key management (with backup & recovery), per-device session ratchets (Signal Protocol), an inability to do server-side moderation (the whole point of content scanning + reports), and operational pain when keys are lost. The trade for v1 is server-side encryption at rest (Postgres TDE, Cloudflare-fronted TLS in transit) plus a published policy that admins can read flagged messages in defined moderation contexts.

Index summary (most load-bearing)

  • UNIQUE INDEX uk_conversation_direct_key on conversation(direct_key) WHERE type='DIRECT' — race protection for first send.
  • UNIQUE(blocker_id, blocked_id) on user_block — idempotent blocks.
  • INDEX on conversation_participant(user_id) + (conversation_id, user_id) — every inbox query reads these.
  • INDEX on message(conversation_id, created_at DESC) — thread pagination cursor.

4.2 — The direct_key trick

The naive "find-or-create DIRECT conversation" is a classic race: two senders click "send first message to X" at the same millisecond, both find no existing conversation, both try to INSERT, both succeed, the user now has two conversations with the same person. Refreshing the inbox shows duplicates that can never merge cleanly.

The fix is migration 039: a deterministic direct_key column that's a SHA-256 of the two participant UUIDs (sorted) plus a partial UNIQUE index. Same two users → same key → exactly one row can ever exist.

// src/modules/messaging/messaging.service.ts (excerpt)
private async findOrCreateDirectConversation(
  aId: string,
  bId: string,
  tx: Transaction,
): Promise<Conversation> {
  const directKey = directKeyFor(aId, bId);     // sha256(sorted([a, b]))
  const existing = await this.conversationModel.findOne({
    where: { type: ConversationType.DIRECT, directKey },
    transaction: tx,
  });
  if (existing) return existing;

  // Create inside a SAVEPOINT. If the UNIQUE(direct_key) index trips
  // because a concurrent sender beat us, only the savepoint rolls
  // back — the outer tx remains usable for the retry read.
  try {
    return await this.sequelize.transaction(
      { transaction: tx },
      async (sp) => { /* ... create conv + 2 participants ... */ },
    );
  } catch (err) {
    if (err instanceof UniqueConstraintError) {
      const winner = await this.conversationModel.findOne({
        where: { type: ConversationType.DIRECT, directKey },
        transaction: tx,
      });
      if (winner) return winner;
    }
    throw err;
  }
}
Why the savepoint

Postgres aborts the entire transaction on a unique-constraint violation. Without the savepoint, the catch-block's retry read would fail with "current transaction is aborted, commands ignored until end of transaction block". The savepoint scopes the rollback to just the failed create, leaving the outer tx healthy.

4.3 — Soft delete vs tombstone

Messages soft-delete: deleted_at + deleted_by_id are set, the body is replaced with the literal tombstone "[deleted]", and the row stays for thread continuity. The FE never has to compute the tombstone — the BE returns it. Soft delete is reversible only at the DB level; the BE does not expose an undelete route.

5 · End-to-end flows

5.1 — Send a message

  1. FE composer calls store.sendMessage({ conversationId, recipientId, body }). Trims body, honours active rate-limit window.
  2. Optimistic insert: a temp bubble with id "optim-…" is added to the active thread.
  3. POST /messaging/messages hits the BE. Sender + recipient are loaded in parallel.
  4. Safety gate: MessagingSafetyService.canMessage() walks the decision tree — am I suspended? does the recipient block me? does the new-account rule apply? am I rate-limited?
  5. Content scan: pure function over the body, always runs. Returns { urls, hasShortenerUrl, hasOffPlatformContact, hasPaymentHandle, anyFlag }.
  6. findOrCreateDirectConversation: the deterministic-key + savepoint pattern from §4.2.
  7. Insert the message row + update conversation.last_message_at / last_message_preview, all inside one transaction.
  8. After commit: EventsService.emitMessageCreated + NotificationService.notify + VelocityService.recordSendAndMaybeAlarm all run post-commit so a rollback never orphans live state.
  9. FE receives 201: optimistic bubble is swapped for the canonical row; threat banner appears if anyFlag; the inbox row promotes to top.

5.2 — Receive a message (SSE)

The recipient's EventSource at /messaging/stream?token=<jwt> receives a message.created event. The FE store handles it via applyMessageCreated:

  • De-dups against the optimistic insert (skips when senderId === currentUserId).
  • If the conversation is currently being viewed, appends to the thread cache and schedules a debounced markRead.
  • Otherwise, bumps the inbox row's unread count.
  • If the conversation isn't in the inbox at all (first message from a stranger), calls getConversation() to materialise it.
  • Acks the event via POST /messaging/stream/ack so the BE can prune its per-user replay buffer.

5.3 — Block a user

  1. From the conversation rail, user clicks Block. The confirm dialog opens.
  2. On confirm, FE calls store.blockUser({ blockedId, reason, conversationId }).
  3. The store hits POST /messaging/blocks. The BE inserts the user_block row.
  4. On success, the store: removes the conversation from the inbox, drops messages/drafts/threat-flag caches, navigates away if it was active.
  5. Future sends from the blocked user are silent-dropped by the BE — they get a 201 with a synthetic conversation shell and never see the block.
  6. To unblock: /profile?tab=safety → click Unblock on the row. Calls DELETE /messaging/blocks/:blockedId.

5.4 — Mute a conversation

Mute writes conversation_participant.muted_until on the actor's row only — never on the other side's. The BE emits a conversation.muted SSE event to the actor themselves so other tabs sync. Muting an indefinite "forever" uses the sentinel ISO '2099-12-31T23:59:59.000Z'. Unmute passes untilIso: null.

Mute does NOT suppress notifications today

Muting affects the local indicator and (in the future) email throttling. The BE's email-send worker does not currently check muted_until before sending the MESSAGE_RECEIVED email — see §14, item 1.

5.5 — Report a conversation

The report dialog collects a category (SPAM / SCAM / HARASSMENT / IMPERSONATION / SEXUAL / OTHER) and optional notes. Calls POST /messaging/reports. The BE:

  1. Resolves the report target (the other DIRECT participant, or the sender of a specific message).
  2. Gates on participant membership — the reporter MUST be in the conversation. Otherwise anyone with a leaked conversation UUID could file abuse reports.
  3. Checks the dedup rule (one OPEN report per reporter+target+conversation).
  4. Writes a message_report row with status OPEN and a velocity alarm if applicable.

5.6 — Silent-drop (block leakage protection)

If the BE returned a 404 when the recipient had blocked the sender, the sender could probe "who blocked me" by mass-sending. So the BE always returns a 201 with delivered: false and a synthetic conversation shell that doesn't persist. The FE's sendMessage handles this:

  • If !res.delivered && conversationId: keep the optimistic bubble visible (swap for canonical row), show inline sendError: "Message couldn't be delivered. They may have left or blocked messages from you."
  • If !res.delivered && !conversationId (from the picker): exit compose mode so the user isn't trapped on a frozen screen.
  • Never upsert the synthetic conversation into the inbox. Never navigate to it (it 404s on click).

5.7 — Cold-load & mark-read

"Cold load" = the user arrives at /messages/:id via permalink before the conversation list has loaded. activeConversation() is null until the list lands. The route subscriber calls markReadOnEntry(id) unconditionally — the BE markRead is idempotent (sets last_read_at = NOW()) so it's safe to call even when local state has nothing to update. Without this, the unread cursor would lag behind.

5.8 — markRead callsite policy

There are three places markRead could fire:

  1. openConversation(id) — clicking a row in the inbox.
  2. ConversationPane route subscriber — entering /messages/:id.
  3. applyMessageCreated — SSE message arrives while the conversation is being viewed.

To avoid 3× PATCH per click (audit finding FE-C4), only the route subscriber owns mark-on-entry. openConversation just navigates and trusts the subscriber to fire. applyMessageCreated uses a 1.5s debounced scheduleLiveMarkRead so a burst of incoming messages coalesces into one PATCH.

6 · Safety pipeline

MessagingSafetyService.canMessage(senderId, recipientId) is the single source of truth. It walks:

  1. Suspension? Is the sender currently within an active messaging_suspension window? → throw 403 (visible to sender).
  2. Blocked by recipient? Does user_block(blockerId=recipient, blockedId=sender) exist? → silent-drop (NOT 403). The sender must never learn they were blocked.
  3. Blocked the recipient yourself? Symmetric check — if A blocked B, A cannot send to B either. Treated as 403 "You blocked this user."
  4. New-account rule? Account created < 24h ago and sender is not an INSTRUCTOR? → 403. Reduces spam-account abuse.
  5. Rate limit? Per-user 30/min, per-conversation 10/sec — see §7.

The content scanner (MessagingContentService.detectThreats) is not a gate — it always runs and returns flags. The FE shows the warning banner to the sender; the recipient never sees it (BE deliberately doesn't broadcast threat flags via SSE).

Content-scan rules

FlagWhat triggers it
urlsAny URL pattern (http/https/www. + bare-domain heuristic).
hasShortenerUrlDomain matches the known shortener set (bit.ly, tinyurl.com, t.co, etc.).
hasOffPlatformContactPhone numbers (E.164-ish), Telegram/Signal/WhatsApp handles, "DM me on X" patterns.
hasPaymentHandleRevolut/PayPal/Venmo/CashApp handles, IBANs, "send to @user" patterns.
anyFlagTrue if any of the above produced a hit — even a plain non-shortener URL.
FE banner empty-reason fallback

If anyFlag is true but only urls matched (no shortener / contact / payment), the FE banner reads "Your last message contains a link." instead of an empty list. See threat-banner.ts.

7 · Rate limiting

An in-memory sliding-window rate limiter (messaging-rate-limit.service.ts) with three windows:

KeyLimitWindow
per-user send3060 s
per-conversation send101 s
per-(recipient, conversation) email160 min

On hit, the BE throws 429 with a retryAfter field in the response body. The FE composer reads it, sets sendRateLimitedUntil, and disables the input with a countdown tooltip.

In-memory means state resets on deploy

Restarting the API zeroes the buckets. Acceptable for v1 because we deploy infrequently, but plan to swap for Redis when we scale to multiple API instances or deploy hourly. The interface is intentionally narrow (assertSendAllowed / shouldSuppressMessageEmail) so the Redis swap is mechanical.

Velocity alarm (separate from rate limit)

An informational alarm fires when a single user sends > 100 messages in 60 min. It does NOT block — it just writes a messaging_velocity_alarm row for admin review. After the audit, the counter is read from the message table directly (not the in-memory rate-limit bucket, which is capped at 30/min and could never reach 100).

8 · SSE: replay buffer, auth, reconnect

Auth

EventSource can't set headers, so the JWT goes in ?token=<jwt>. A dedicated Passport strategy 'messaging-sse' accepts query-string tokens. It's named only for the SSE endpoint — applying AuthGuard('messaging-sse') anywhere else would be a security bug (query-string tokens leak via browser history, referrer headers, proxy access logs). Grep for the literal 'messaging-sse' to verify there is exactly one call site.

Replay buffer

An in-process ring buffer per user: 100 events, 10-minute TTL. On reconnect, the browser sends Last-Event-ID; the BE returns the events after that id from the buffer, then continues with live events. Heartbeats are NOT buffered (no value to replay).

What breaks at scale

The EventEmitter2 bus + the replay buffer are single-process. The day we run two API instances, a user connected to instance A won't see events emitted by instance B. The plan is to swap to Redis Pub/Sub when that lands — search for "swap the implementation for a Redis Pub/Sub adapter" in messaging-events.service.ts.

Reconnect with network awareness

The FE realtime service handles two failure modes:

  • Token expiry / transient server error: EventSource emits error, readyState flips to CLOSED. We schedule a 3-second backoff, then re-open with a fresh token (which the auth interceptor has refreshed in the meantime).
  • Offline: navigator.onLine === false. We do NOT spam reconnect attempts — we attach a one-shot window.addEventListener('online', …) listener and wait for connectivity to return.

9 · Frontend store anatomy

MessagingStore at projects/core/src/lib/stores/messaging.store.ts is the single signal store for the whole feature. It owns:

  • Conversation list, filter / search state, unread badge total.
  • Per-conversation message cache + pagination cursors.
  • Active conversation id (URL is still source of truth — ConversationPane writes it).
  • Composer drafts, send state, rate-limit window, inline error.
  • Threat-flags captured from send responses (sender-only).
  • SSE event fan-in (message.created, .deleted, .read, .muted, heartbeat).
  • Block / mute / report actions.

The auth transition effect

The store is root-scoped so it survives logout/login in the same tab. The auth effect collapses noisy boot sequences into a single load:

effect(() => {
  const isAuthed = this._auth.isAuthenticated();
  const userId = this._auth.user()?.id ?? null;
  const sameAuthState = isAuthed === this.lastAuthState;
  const sameUser = userId === this.lastAuthedUserId;
  if (sameAuthState && sameUser) return;

  this.lastAuthState = isAuthed;
  this.lastAuthedUserId = userId;

  if (!isAuthed) { this.onLogout(); return; }
  if (!sameUser) this.reset();   // identity changed → drop residual state
  this.onLogin();
});

The user-id check guards the rare case where the auth state transitions true → true (different account). Without it, residual messages / drafts from the previous identity would be visible to the new user.

LRU cache for messages

Switching through 50+ conversations would otherwise keep every thread's full message array in memory until logout. The store touches an LRU on every patchMessages call; when the cache exceeds MAX_CACHED_CONVERSATIONS (10), the least-recently-touched conversation is evicted — but never the currently-active one.

Optimistic send + rollback

const optimisticId = `optim-${cryptoRandom()}`;
this.patchMessages(conversationId, {
  items: [...this.messagesFor(conversationId).items, optimistic],
  hasLoaded: true,
});

this._api.sendMessage(recipientId, trimmed).pipe(
  tap((res) => {
    // Race guard: blockUser may have dropped this conversation
    // while we were in flight. If so, don't re-create caches.
    if (conversationId && !this._conversations().some((c) => c.id === conversationId)
        && !(conversationId in this._messagesByConv())) {
      this._composerDraft.update((all) => omitKey(all, draftKey));
      return;
    }
    // Replace optimistic bubble with the canonical row.
    this.patchMessages(conversationId!, {
      items: this.messagesFor(conversationId!).items.map((m) =>
        m.id === optimisticId ? res.message : m,
      ),
    });
  }),
  catchError((err) => {
    // Strip the optimistic bubble on failure.
    if (conversationId) this.patchMessages(conversationId, {
      items: this.messagesFor(conversationId).items.filter((m) => m.id !== optimisticId),
    });
    /* … 429 / 403 / 400 / 0 / 5xx handling … */
  }),
).subscribe();

Notification channel policy

MESSAGE_RECEIVED notifications always set channelOverride.in_app = false. Reason: the Messages sidebar badge is the persistent in-app signal — a bell entry would duplicate it. Email is gated by an hour-window throttle so the user gets one email per (recipient, conversation) per hour, regardless of message volume.

10 · Coding standards in use

Every standard below is enforced by the existing CLAUDE.md and was followed throughout messaging.

  • Thin controllers: request → service call → response. No business logic.
  • DTOs everywhere: class-validator on input, PaginationDto as the base for list params.
  • ParseUUIDPipe on every UUID @Param. A bare :id would let a malformed UUID 500 in Sequelize.
  • Underscored tables: conversation_participant, message_report, etc. Entities use underscored: true.
  • Transactions: every multi-table write wrapped in a tx. Every ORM call inside passes { transaction: tx } explicitly.
  • notify-after-commit: NotificationService.notify(...) always runs after the surrounding tx commits. For webhook-style flows we don't own, use NotificationOutbox.
  • Builders, never literals: producers call notify(messageReceived(...)), not an object literal. Builders take primitive arguments only.
  • data.screen + queryParams: notifications use { screen: 'messages', queryParams: { conversationId } } rather than entityId (matches the FE routing convention).
  • Pagination shape: { items, total, page, pageSize } — frontend contract, never change.
  • Errors: NestJS built-ins (NotFoundException, BadRequestException, ConflictException, etc.). Never throw new Error().
  • Signal-based FE state: signal(), computed(), effect(). Reads in templates are store.foo() — never inject a BehaviorSubject.
  • Standalone components: every component has standalone: true (implicit in Angular 21 but explicit for clarity).
  • OnPush change detection everywhere — signals work natively with it.
  • kebab-case file names, PascalCase classes, UPPER_SNAKE enum values.

12 · Common pitfalls when building messaging

Pitfall 1 — First-send race

Two users hit "send first message" at the same instant. Without a deterministic key + UNIQUE index, both create rows and the user ends up with duplicate conversations. We solved this with direct_key + a savepoint-protected retry. See §4.2.

Pitfall 2 — Block leakage via 404

If "you blocked me" returns 404 and "you don't exist" returns 404 but "you exist and accept messages" returns 201, an attacker can probe arbitrary user IDs. Solution: ALL three return 201 with delivered: false; only the blocker's UI ever changes. The sender can never distinguish.

Pitfall 3 — Aborted transaction retry

Postgres aborts the entire transaction on a unique-constraint violation. A retry read inside the same tx fails with "current transaction is aborted, commands ignored until end of transaction block". The savepoint-based retry pattern in §4.2 is the fix.

Pitfall 4 — Triple markRead on entry

It's easy to call markRead from three places: the click handler, the route subscriber, and the SSE-message handler when the conv is active. Result: three PATCH requests per click. Pick a single owner (we chose the route subscriber) and debounce live-arrival marks.

Pitfall 5 — Notify inside the transaction

If notify() runs inside the surrounding tx and the tx rolls back, you've fired a notification for a message that doesn't exist. Always run notifications after commit. For webhook flows you don't own, use NotificationOutbox + flush() on commit / discard() on rollback.

Pitfall 6 — N+1 in inbox refresh

Computing unread counts via one COUNT(*) per conversation is fine for 5 conversations and a disaster for 500. Either use a single grouped query (SELECT conversation_id, COUNT(*) … GROUP BY) or denormalise an unread counter on the participant row.

Pitfall 7 — SSE retry storm while offline

EventSource reconnects forever on error. Combined with a 3-second backoff and an offline browser, you'll churn a connection every 3 seconds. Check navigator.onLine + attach an online listener; suspend the timer when offline.

Pitfall 8 — Cache leaks

An unbounded per-conversation message cache + per-conversation drafts + per-conversation threat flags will grow forever in a long-running tab. LRU-bound them and evict caches together (a conv that's not in memory shouldn't have a draft floating around either).

Pitfall 9 — Stale pagination cursor

A user scrolls back into history; the cursor message has since been moderator-deleted. The BE 400s with "cursor not found", the FE swallows it, and "Load earlier messages…" spins forever. Always handle the 400 by clearing nextBefore so the affordance hides.

Pitfall 10 — Cross-user state leak in a long-lived tab

If your store is root-scoped (one instance for the app lifetime), logging out and back in as a different user can leak messages/drafts from the previous identity. Track the auth state AND the user id; reset on identity change even when the auth state transition was true → true.

Pitfall 11 — Mute that doesn't mute notifications

A user mutes a conversation, then gets emailed every message. Make sure the notification builder checks muted_until before suppressing or short-circuiting the email channel. (We have this gap today — see §14.)

Pitfall 12 — Optimistic insert that doesn't roll back

Add a fake "sent" bubble, the POST fails, the bubble stays forever with no error. Roll back the optimistic insert on every error branch — 429, 403, 400, 0 (offline), 5xx — and surface an inline error so the user knows.

Pitfall 13 — One PATCH per incoming message in a busy thread

If you call markRead every time SSE delivers a message while the user is viewing the thread, a chat-heavy moment becomes a PATCH storm. Debounce the live mark-read (we use 1.5 s).

Pitfall 14 — Velocity counter from an upper-bounded source

If your ">100 msgs in 60 min" alarm reads from a counter that's capped at 30 (because of the per-minute rate limit), the alarm can never fire. Query the table directly, or maintain an independent counter.

Pitfall 15 — Query-string token strategy bleed

A Passport strategy accepting ?token= tokens is globally registered. If any other endpoint accidentally uses AuthGuard('that-strategy'), it suddenly accepts query-string auth too. Name the strategy something obviously scoped (we use 'messaging-sse') and grep before merge.

13 · Future maintenance hotspots

Things that work today but will need attention as load grows or features arrive:

  1. Mute doesn't suppress notifications. notification.service.ts needs a check against conversation_participant.muted_until before queuing the MESSAGE_RECEIVED email. Today muted users still receive emails.
  2. SSE replay buffer is single-process. Swap messaging-events.service.ts for a Redis Pub/Sub adapter the day we deploy a second API instance. The interface is the seam — preserve it.
  3. Rate-limit buckets are in-memory. Same as above — a restart resets every counter. Move to Redis when scaling out.
  4. Unread count is N+1. getUnreadCount fires one COUNT(*) per conversation. With 50+ conversations per active user, this becomes a hot spot. Switch to a grouped query or denormalised counter.
  5. SSE auth: no proactive token refresh. The realtime service waits for an SSE error before reconnecting with a new token. An idle user with no REST traffic for an hour will get a forced reconnect then. Consider a proactive setTimeout < the JWT expiry to call reconnect().
  6. FE has no test infra. Set up Jest (or Karma → Jest migration) for projects/core + projects/web, then add the spec list from §11.
  7. Per-message reporting is wired BE-side, missing FE. Add a kebab menu on each message-bubble bubble to report a specific message (the BE already accepts messageId).
  8. Groups schema is ready, no UI. When groups land: create-group page, member rail, role management, SYSTEM_* event rendering in the thread.
  9. Indefinite mute uses a sentinel ISO. '2099-12-31T23:59:59.000Z' is fine but fragile. Migrate to a nullable muted_indefinitely boolean OR document the sentinel in the DTO.
  10. Velocity table-count is one extra query per send. Cheap today but could be moved out-of-band (background worker reading the audit log).
  11. Soft-deleted messages accumulate forever. No purge job runs. Add a nightly task that hard-deletes message rows with deleted_at < NOW() - INTERVAL '90 days' (or whatever the retention policy is).
  12. Admin moderation UI is missing. Reports go to a queue with no review tooling. The BE routes exist; build a /super-admin/messaging/reports page.

15 · Known gaps & v2 roadmap

Explicitly out of scope for v1

  • Group conversations (schema-ready, no UI).
  • Typing indicators.
  • Presence (online / offline / last-seen).
  • File / image / voice / video attachments.
  • Reactions, threaded replies, in-conversation search, read-receipts popover.
  • Per-message reporting UI (BE accepts messageId; FE only sends conversationId).
  • Admin-side moderation UI (separate "support tools" feature).
  • End-to-end encryption.
  • Push / SMS notifications.

v2 priorities (rough order)

  1. Mute → silence email notifications (one-line fix in the notification builder, but it's load-bearing for UX).
  2. Admin moderation UI consuming the existing BE routes.
  3. Group conversations (the biggest single feature) — needs create-group page, member rail, role gating.
  4. Redis Pub/Sub adapter for MessagingEventsService and the rate-limit buckets (unlocks multi-instance deploys).
  5. FE test infra (Jest), then the spec list from §11.
  6. Per-message reporting on the FE.
  7. Push notifications via the existing Bull queue (pending Jobs module).
  8. Soft-deleted message purge job (90-day retention).

16 · Glossary & file map

Glossary

Conversation
A thread. v1 only creates DIRECT; GROUP is schema-ready.
Participant
A row in conversation_participant tying a user to a conversation. Owns per-user metadata: last_read_at, muted_until, left_at.
Direct key
SHA-256 of the sorted UUID pair. Deterministic, unique per (a, b). Prevents first-send races.
Silent drop
The BE returns 201 with delivered: false and a synthetic conversation shell when the recipient is blocking the sender (or doesn't exist). Prevents block-status leakage.
Tombstone
The literal string "[deleted]" that replaces a message body on soft-delete.
Threat flags
BE-computed signals on the content of a sent message. Sent only to the sender; never broadcast.
SSE replay buffer
In-process per-user ring of recent events (100 entries, 10 min TTL). Used to fill the gap on a reconnect.
Optimistic insert
FE adds a temporary message bubble with an "optim-…" id before the BE responds; replaces with the canonical row on 201 or strips on error.
notify-after-commit
Pattern: always call NotificationService.notify(...) AFTER the surrounding tx commits, never inside.
messaging-sse strategy
The Passport strategy that accepts a JWT from ?token=. The verbose name is intentional — it must be obvious in code review.
Velocity alarm
An informational row written when a user sends >100 messages in 60 min. Does NOT auto-block.
