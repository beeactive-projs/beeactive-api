Redis: connections, memory & the limit alert action needed

MotionHive jobs system • Redis Cloud Essentials 30 MB (free tier) • why motionhive-dev keeps hitting 103% and how to fix it.

TL;DR — read this first

  • The alert is about connections, not memory. The email says "number of connections … reached 103.33% of the connections limit." The 30 MB is your data ceiling; the 30-connection cap is a separate limit, and that's the one you're hitting.
  • BullMQ is connection-hungry. Every queue and every worker opens its own Redis connection(s). With 5 queues + 5 workers we use ~15 connections per running app instance.
  • The spikes happen on deploy. During a rolling restart, the new instance opens its ~15 connections before the old one finishes closing → momentarily ~30 → over the free-tier cap. That's your "some moments when this is over limit."
  • A second free subscription only helps if dev and prod currently share one Redis. It does not raise a single app's 30-connection ceiling.
  • Durable fix: share one Redis connection for queues + collapse 5 queues → 2, and/or move to a small paid tier (≈$5/mo → 256 connections). Details below.

1. How the workers & queues are split

The jobs system runs in-process (same Node app as the API). There are 5 BullMQ queues, each owned by exactly one worker (a NestJS @Processor class), plus cron schedulers that only enqueue jobs — they don't touch Redis connections directly.

QueueWorker (@Processor)Jobs it runsTrigger
notificationsEmailSendWorker email_send Enqueued live by NotificationService (every in-app/email notification)
sessionsSessionsWorker reminder_dispatch, status_transition, generate_recurring, cleanup_stale_participants Cron: 5m / 5m / daily / hourly
workoutsWorkoutsWorker auto_skip_past_workouts, auto_complete_assignments Cron: daily 02:00 / 02:30
paymentsPaymentsWorker invoice_due_soon, invoice_overdue, card_expiring, earnings_summary, refund_window_closing, dunning, dispute_deadline, balance_cache_refresh, process_webhook, reconcile_webhooks Cron (06:00–08:00, hourly, 30m) + live (webhook processing)
maintenanceMaintenanceWorker cleanup_refresh_tokens, cleanup_lockouts, cleanup_invitations, cleanup_client_requests Cron: daily 04:00–04:30

One @Processor class per queue; multi-job queues route by job.name internally (the MultiJobWorker pattern). Schedulers (@Cron) call JobsService.enqueue() — they reuse the queue connection, they don't open new ones.

2. How Redis connections actually get used root cause

This is the important part. In BullMQ each component opens its own TCP connection(s) to Redis — and because our config passes a plain options object rather than a shared client, nothing is reused:

// src/app.module.ts — current config: a NEW connection per queue + per worker
BullModule.forRootAsync({
  useFactory: (cfg) => ({
    connection: { host, port, password, tls }   // ← plain object → not shared
  })
})

Why a worker needs more than one connection

A BullMQ Worker can't do everything on one socket: it holds one connection blocked on BZPOPMIN (waiting for the next job) and needs a second connection for normal commands (ack, move to completed, update counters). A Queue (the producer side) needs one. So:

ComponentCountConns eachTotalWhy
Queues (producers)5~1~5command connection for enqueue / Bull Board reads
Workers (consumers)5~2~101 blocking + 1 commands
Bull Board (when dashboard open)5~1+~5a QueueEvents stream per queue for the live UI
Per app instance (baseline, dashboard closed)~15
Per app instance (dashboard open)~20

Exact numbers depend on BullMQ internals and whether the dashboard is open; treat these as "~". The shape is what matters: connections scale with (queues + 2×workers).

Why it crosses 100% only "sometimes"

One steady instance at ~15 is comfortably under 30. The problem is overlap:

DEPLOY / RESTART TIMELINE (free-tier cap = 30 connections) old instance ████████████████ ~15 ───────────┐ draining (app.close on SIGTERM) new instance ┌── ~15 starting up ▼ combined ███████████████████████████████ ~30+ ← ALERT 103% └─ both alive for a few seconds during the rollover

Your graceful shutdown is wired (SIGTERM → app.close() closes the workers), so the old connections do release — but not instantly, and the new instance is already up. The same doubling happens if Railway ever runs 2 replicas, or if dev and prod both point at the same Redis.

👉 First thing to check: does your production app use a different REDIS_HOST than motionhive-dev? If prod is pointed at the dev Redis, you have two apps × ~15 = ~30 connections all the time, and that alone explains it. They must be separate instances.

3. The memory side (the 30 MB) — not the current alert, but the next wall

Redis also stores the job data. Each job is a hash holding its payload + metadata, kept around per the retention caps in job-registry.ts:

QueueremoveOnCompleteremoveOnFail
notifications1 day / 1,0007 days / 5,000
payments1 day / 1,0007 days / 5,000
sessions / workouts1 day / 5007 days / 2,000
maintenance1 day / 2007 days / 1,000

Most jobs are tiny (a few hundred bytes). The one to watch is payments.process_webhook: today its payload carries the entire verified Stripe event (2–10 KB each) so account-level events keep their event.account field.

Worst case: 5,000 failed payment jobs × ~5 KB ≈ ~25 MB of the 30 MB budget — just from retained failed webhook jobs. Normally far less, but a burst of webhook failures could push you to the memory wall too.

4. How to fix it — ranked

Fix 1 Share one Redis connection for the queues ~30 min · biggest easy win

Pass a single shared ioredis client instead of an options object. Queues then reuse one connection (5 → 1). Workers still each need their own blocking connection, but the command side can share too. Expect to drop from ~15 → ~7–8 per instance.

// app.module.ts
import IORedis from 'ioredis';

const sharedConnection = new IORedis(redisUrl, {
  maxRetriesPerRequest: null,   // required by BullMQ
  enableReadyCheck: false,
});

BullModule.forRootAsync({
  useFactory: () => ({ connection: sharedConnection }),  // ← shared instance
});

Fix 2 Collapse 5 queues into 2 ~half a day · biggest structural win

Connections scale with the number of queues/workers, not the number of jobs. We don't need per-domain queues at this scale. Merge into:

  • scheduled — all cron sweeps (sessions, workouts, payments-reminders, maintenance). One worker, routes by job name.
  • events — latency-sensitive live work (email_send, process_webhook).

2 queues + 2 workers ≈ ~4–6 connections total. Combined with Fix 1 you'd sit around 3–5 — miles under 30, with headroom for deploy overlap. (The MultiJobWorker we already use makes this a mechanical change: same handlers, fewer @Processor classes.)

Fix 3 Don't let connections double on deploy config

  • Single replica + "recreate" (stop-then-start) instead of rolling/overlap on the dev service, so the old instance is gone before the new one boots. (On Railway: 1 replica; ensure the old deploy is fully stopped — health-check based cutover keeps both alive briefly.)
  • Keep workers off extra web replicas later via a WORKER_KIND env flag (the hook is already noted in jobs.module.ts): run @Processors only on one process; web replicas just enqueue.

Fix 4 Trim the memory hot-spot if/when memory becomes the wall

  • Store only webhookEventId in the process_webhook payload and reload the event from the webhook_event DB row in the worker (drop the full-event copy from Redis). Keep just event.account alongside the id for the account.* case.
  • Lower removeOnFail counts (e.g. payments 5,000 → 500). Failed-job history also lives in the webhook_event table, so Redis doesn't need to be the archive.

5. "Can I just create one more free subscription?" honest answer

✅ When a 2nd free DB helps

If dev and prod currently share one Redis, a second free subscription lets you give prod its own 30 MB / 30-connection budget, separate from dev. Each app then has its own ceiling instead of fighting over one.

❌ What it does not do

It does not raise a single app's 30-connection limit. One MotionHive instance using ~15 connections is fine; but with deploy overlap (~30) you'll still spike. A second free DB doesn't change that for the same app.

So: a second free sub is a reasonable band-aid to isolate dev from prod, but the real fix is Fix 1 + Fix 2 (fewer connections per app). If you'd rather not refactor, the cheapest durable option is a paid Essentials tier (~$5/mo) which raises the connection cap to 256 and memory to 100 MB+ — that removes the ceiling entirely for our scale.

6. Recommended plan

1
Verify isolation. Confirm prod's REDIS_HOST ≠ motionhive-dev. If they share, point prod at its own Redis (or a 2nd free sub) today — that may be the whole problem.
2
Apply Fix 1 (shared connection). Small, safe, ~halves connections. Ship to dev, watch the connections graph in the Redis Cloud dashboard for 24h.
3
Apply Fix 3 (single replica / recreate deploys) so rollovers don't double the count.
4
If still tight, do Fix 2 (5 → 2 queues). After this you're at ~3–5 connections and the free tier is comfortable.
5
Keep an eye on memory. If the 30 MB starts filling, apply Fix 4 (trim the webhook payload + lower removeOnFail). Otherwise leave it.
6
If you want zero ceiling worry: ~$5/mo Essentials (256 connections / 100 MB). Cheapest path that needs no code change.

How to read the Redis Cloud dashboard

Login → your subscription → Metrics. Watch two graphs:

  • Connections — should sit flat around your baseline (~15 now, ~5 after fixes). Spikes = deploys or a second app sharing the DB.
  • Used memory — should stay well under 30 MB. If it climbs and doesn't fall after a day, it's retained failed jobs (Fix 4).

You can also run CLIENT LIST / INFO clients from the Redis console to see exactly who's connected (each BullMQ connection shows its name).
