The exercise catalog — browse 870, create your own, fork the best.

A mid-fi spec for the Exercises module (S1–S8). Mobile-first, built on MotionHive's existing shell — the same top bar, sidebar, 5-tab bar, bottom sheets and FAB you already ship. Every screen is annotated with the product call it makes and the schema fields it touches, so this doc cross-checks directly against the migration. Visual polish is deliberately restrained; the priority is UX decisions and data shape.

Where Exercises lives, and who can do what

Before the screens: two decisions that shape every one of them — where the module sits in navigation, and how the ownership/visibility rules translate into visible affordances.

ANavigation placement

Exercises is an instructor building-block, not a social surface — it belongs with the coaching tools, not next to Discover/Home. On desktop it gets a top-level item in the Coaching group of the sidebar. On mobile the 5-tab bar is full (Home · Discover · Sessions · Messages · More), so Exercises lives one level in under More, and — because instructors hit it constantly while programming — also surfaces as a shortcut on the Coaching hub. My exercises is not a separate nav item; it's an ownership filter inside the catalog (see S1/S6).

The picker reuses the catalog. S7 (add-exercise from the program builder) is the same data and filters as S1 in a sheet/drawer. One catalog, three entry points: Coaching → Exercises, More → Exercises, and "Add exercise" inside a workout.

1

Infinite scroll, not pages

Browsing is exploratory and thumb-driven on the gym floor — page chrome breaks the scroll rhythm. An IntersectionObserver sentinel loads the next 24 as you near the bottom.

"Most-forked" still works: it's just the sort order of the same infinite stream, with the fork count on each card. A result-count header ("410 results") gives the sense of scale that pagination usually provides.

Confirmed with you
2

Filters: rail on desktop, sheet on mobile

Desktop has the horizontal room for a persistent left rail with live counts — instructors refine without losing the grid. Mobile collapses it into a bottom sheet behind a "Filters · N" chip, so the list keeps full height and scroll position.

Decision
3

Ownership is tabs; everything else is filters

All / System / My exercises / Public-from-others is the one facet users switch between as a mode, so it gets pill tabs at the top — not buried in the filter sheet. It doubles as the entry to S6 (My exercises).

Decision
4

Grid desktop · list mobile (toggle either way)

Grid shows thumbnails large enough to recognize a movement at a glance; the dense list packs ~7 rows on a phone. A view toggle lets power users flip to list on desktop for scanning long result sets.

Decision
5

Skeletons, not spinners

The card shape is known, so the first load paints card-shaped skeletons (see S8) — perceived speed beats a centered spinner. Subsequent infinite-scroll batches use a small inline spinner at the sentinel.

Decision
6

Create CTA is always one tap away

Desktop: a primary button in the header. Mobile: the standard honey FAB. It also appears contextually inside the empty state and the picker (S7), because "I can't find it" is the strongest moment to author one.

Decision
S2 Exercise detail

One layout, role-aware actions. Where the data breathes.

Same screen for instructor and client — the client simply has no edit/fork bar. Hero media up top, then muscles, equipment, instructions, with classification metadata kept secondary. The action bar is what changes by ownership.

1

Single page beats a wizard

The field set is shallow and mostly optional. A wizard adds steps and hides the "required vs optional" shape that lets a power user fill three fields and save. Smart defaults (Bodyweight, kind→mechanic/force) shrink it further.

Decision
2

Muscle role is a property of the chip

Pick the muscle once, then set Primary/Secondary/Stabilizer on its chip. Beats three separate multi-selects (which let you assign the same muscle conflicting roles) and beats a body-map (heavy to build, overkill for a text-first catalog).

Decision
3

Kind teaches as it selects

Each of the 6 kinds is a card stating what gets logged ("Reps + weight", "Time only"). It's the field that drives logging downstream, so the consequence is shown at the point of choice.

Decision
4

Two saves, no draft

"Save" exits to the new exercise; "Save & add another" clears and keeps the sheet open for batch authoring. No explicit draft state — an exercise is cheap to keep Private and finish later, so Private is the draft.

Decision

Fields needed — candidates for the migration

Things the UI wants that aren't in the schema as written. These are the cheap-to-decide-now / expensive-to-add-later items — please confirm before locking.

!

fork_count

Shown on cards, detail ("Forked by 42"), My exercises, and drives the "most-forked" sort. Derivable by counting rows where forked_from_id = x, but needs to be queryable/sortable — likely a denormalized counter on the exercise.

!

created_at / updated_at

The "Newest" sort and any "recently edited" affordance need timestamps. Not listed in the schema — assumed present as standard audit columns; please confirm they're exposed on the payload.

!

Author identity (denormalized)

Schema has owner_id only. Attribution needs the owner's display name, avatar, and profile slug ("Created by Diana Marin → profile"). Either expand owner in the payload or denormalize owner_name/owner_slug.

!

forked_from name + slug

"Forked from [Original Exercise]" is a link — it needs the source's name and slug, not just forked_from_id. Expand the relation or denormalize a small {id,name,slug}.

!

Start + end images for SYSTEM

The brief says two static JPGs (start + end) exist per system exercise, but the schema has a single thumbnail_url. We need either image_urls[] or explicit start_image_url/end_image_url — and a rule for which one is the catalog thumbnail.

?

Faceted filter counts

The filter rail shows live counts ("Strength · 410"). That's an aggregation the search endpoint must return per facet, not a field — flag the API need, or we drop the counts.

?

Search aliases / synonyms (nice-to-have)

Partial-match on name alone misses "hip thrust" vs "glute bridge". An optional aliases[] would make search forgiving. Low priority, but cheap if added now.

?

Laterality (minor)

Unilateral movements (split squats, single-arm rows) are common; a unilateral boolean would help logging and labelling later. Not blocking — noting it while we're in the schema.

Open questions

Things I had to assume to make the screens concrete. Each has my working assumption in teal — overturn any of them and the affected screen changes.

Can clients browse the full catalog (S1), or only view exercises assigned to them? The brief calls clients read-only "in the catalog context" but doesn't say whether they get the browse hub at all.Assumed: clients reach detail (S2) only from an assigned program; they don't get the S1 browse hub. If they should browse, S1 needs a client variant with no create/fork affordances.
Is fork_count a stored counter or computed on read? It appears on cards, detail and the "most-forked" sort.Assumed: a denormalized counter incremented on fork, so it's sortable without a join.
Do created_at/updated_at exist and ship on the payload? Required for the "Newest" sort.Assumed: yes, standard audit columns exposed to the client.
SYSTEM start/end images — one field or two? Schema has a single thumbnail_url but the seed has two JPGs.Assumed: thumbnail_url is the catalog image (start position); detail shows start + end from an image_urls[] we add.
Can a forked (Private) copy be re-published as Public? Affects the visibility toggle on forks.Assumed: yes — a fork is a normal INSTRUCTOR exercise and can be made Public, keeping its forked_from_id.
