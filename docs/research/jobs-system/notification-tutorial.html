Notification System — Tutorial

A complete walkthrough of the multi-channel notification system in MotionHive — what we've shipped through Phase 4, why we built it this way, what's next, and how every piece fits together. Read top-to-bottom or jump to any section using the nav.

What we built (and why)

The product needs to notify users about things — invoices got paid, sessions are starting, someone wants to be your client. Each notification might appear in several places: the bell icon in the app, an email in their inbox, a push notification on their phone (later), maybe an SMS for high-urgency money events (also later).

The naive approach would be: in the code that creates an invoice, also send the email and create the in-app row. That works for one notification type but explodes when:

  • You have 30 different notification types across 8 modules
  • Each user wants to control which channels they receive (preferences)
  • You want to add a new channel (push, SMS) without changing every producer
  • You want to make these async (move them off the request path)
The pattern we used — borrowed from the clym/events-api reference project (sections C of the research index): producers don't know about channels. They call notify(userId, type, title, body). The notification system writes the in-app row, looks up that user's channel preferences, and fans out to whichever channels are enabled. Adding a new channel later = one new adapter, zero changes to call sites.

This tutorial covers everything we've built through Phase 4 (data model, services, REST API, debug endpoint) and previews what's coming in Phase 5 (frontend bell + settings) and Phase 6 (BullMQ workers + push + real-time).

What's done Phase 1–4

  • 4 services: producer-facing NotificationService + 3 FE-facing services (receipts, preferences, devices)

The 4 tables

Designed to support broadcasts (one alert → many recipients), per-user channel preferences, and multi-device push (web + iOS + Android in one table).

notification — the message itself

One row per event, not per recipient. A broadcast ("session cancelled, notify all 12 participants") is one notification row + 12 receipt rows.

ColumnPurpose
idUUID PK
typee.g. 'INVOICE_PAID' — VARCHAR not Postgres ENUM, so adding a new type is a code change, not a migration
title / bodyWhat the user sees in the bell + email
data (JSONB){ screen, entityId, action } — drives FE deep-linking
severityinfo / success / warn / error — drives icon + color
audience_typeUSER / GROUP / PLATFORM — Phase 4 only emits USER, others reserved for future broadcasts without schema change
fingerprintOptional sha256; same fingerprint within window = no duplicate notification
deliver_at / expire_atScheduled visibility window — bell query honors both

notification_receipt — per-recipient state

One row per (notification, user) pair. Tracks the delivery funnel:

TimestampSet when
delivered_atIn-app worker created the receipt → bell shows it
viewed_atUser opened the bell dropdown and saw it (FE batch-marks on dropdown open)
read_atUser clicked through OR clicked "mark all read"
clicked_atUser followed the deep link to the entity
dismissed_atUser X'd it without reading

Plus delivered_channels JSONB for per-channel audit:

{
  "in_app": "sent",
  "email": "sent",
  "push": "failed:no_active_devices",
  "sms": "skipped:preference_off"
}
Why split notification + receipt? Lets us have one alert row that fans out to many users (broadcast). Edit the message once, all recipients see the update. Storage stays small (no duplicating title/body N times). Read counts, click rates, etc. become trivial COUNT queries on the receipt table.

notification_preference — per-user channel toggles

Sparse. Only contains rows where the user has overridden the system default. The defaults live in code (notification-defaults.ts) so we don't need a migration to retune.

// notification-defaults.ts excerpt
export const NOTIFICATION_DEFAULTS: Record<NotificationType, ChannelPreferences> = {
  [NotificationType.SESSION_REMINDER_1H]: { in_app: true, push: true },
  [NotificationType.INVOICE_PAID]: { in_app: true, email: true },
  [NotificationType.GROUP_MEMBER_JOINED]: { in_app: true },
  // ...30 entries
};

device_token — push registration

One row per (user, device). Web Push subscriptions and mobile FCM tokens live here together. Same query (WHERE user_id = ? AND revoked_at IS NULL) returns everything; the future push worker branches on platform to pick the adapter.

ColumnFor WEBFor IOS / ANDROID
tokenJSON-stringified PushSubscriptionFCM token string
endpoint_hashsha256 of subscription.endpoint URLsha256 of FCM token
last_seen_atBumped on every login + heartbeatSame
revoked_atLogout / push 410 / user removesLogout / FCM NotRegistered / user removes
"How do we know how many devices a user has?" They tell us. Each device registers itself once (POST /devices/register) after the user grants push permission. A user with the web app on their laptop, the web app on their phone browser, and the Ionic app on iPhone has 3 rows.

Producer flow — what happens when notify() is called

This is the heart of the system. When any service in the API needs to notify a user, it calls notificationService.notify(...). Here's the full flow:

src/modules/payment/services/invoice.service.ts (example)
await this.notificationService.notify({
  userId: invoice.userId,
  type: NotificationType.INVOICE_PAID,
  title: 'Invoice paid',
  body: `Your invoice for ${formatMoney(invoice.amount)} was paid.`,
  data: { screen: 'invoice', entityId: invoice.id },
});

Behind the scenes, in NotificationService.notifyMany() ([notification.service.ts:114–214](src/modules/notification/notification.service.ts#L114-L214)):

  1. Dedup userIds — a participant array could contain the same user twice (e.g. instructor is also a member). We Array.from(new Set(userIds)).
  2. Open a transaction for the notification row creation.
  3. Check for existing fingerprint — if the producer passed fingerprint and we've already created a notification with that fingerprint, return the existing one (idempotency).
  4. Insert the notification row. audienceType=USER, audienceId=userId if single recipient (or null for multi).
  5. Commit the transaction. The notification now exists.
  6. Bulk-load preferences for all recipients in one query.
  7. Bulk-load user emails in one query.
  8. For each recipient → deliverToUser():
    • findOrCreate the receipt (UNIQUE on notification_id, user_id — idempotent re-runs)
    • Resolve effective channels (user override merged over system default)
    • If in-app channel enabled: mark delivered_channels.in_app = 'sent'
    • If email channel enabled: call EmailService.sendNotificationEmail(), record success or failure reason
    • Push / SMS: 'skipped:not_implemented' for now (Phase 6+)
    • save() the receipt with the audit
Phase 4 trade-off: the email send blocks the request path. If you call notify() in a controller, the user waits ~300ms for Resend to respond before getting their HTTP response. This is intentional — feeling that latency is the motivation to ship Phase 6 (workers) where the email goes onto a queue and the request returns in 10ms.

Why we don't roll back the in-app row when email fails

If Resend is down for 30 seconds, we'd lose every notification during that window. Instead, we record the failure on the receipt (delivered_channels.email = 'failed:resend 503') and let the in-app row succeed. The user still sees the bell. Later we can add a retry job (Phase 6) that scans for failed channels and re-sends.

How preference resolution works

Two layers, code wins over DB only when DB is missing:

  1. System defaults in notification-defaults.ts — what most users want for each type
  2. User overrides in notification_preference table — only rows the user has explicitly changed

The merger lives in resolveChannels():

export function resolveChannels(
  type: NotificationType,
  override: ChannelPreferences | null,
): Required<ChannelPreferences> {
  const base = NOTIFICATION_DEFAULTS[type] ?? IN_APP_ONLY;
  return {
    in_app: override?.in_app ?? base.in_app ?? true,
    email:  override?.email  ?? base.email  ?? false,
    push:   override?.push   ?? base.push   ?? false,
    sms:    override?.sms    ?? base.sms    ?? false,
  };
}

Why per-key fallback (not whole-row): a user can disable email for INVOICE_PAID without losing the default push setting. Only the channels they explicitly toggle change.

Bell flow — what the FE sees

In Phase 5 the frontend will:

  1. On app load: poll GET /notifications/unread-count every 60 seconds → update the badge on the bell icon
  2. When user clicks bell: GET /notifications?page=1&limit=20 → render the dropdown list
  3. When dropdown opens: PATCH /notifications/viewed with the visible IDs → analytics signal (not "read")
  4. When user clicks a notification: PATCH /notifications/:id/clicked → marks both clicked + read, then router navigates to data.screen / data.entityId
  5. "Mark all read" link: PATCH /notifications/read-all → badge drops to 0
  6. X button on a notification: PATCH /notifications/:id/dismiss → hides from list
  7. Trash icon: DELETE /notifications/:id → hard delete

The settings tab will:

  1. GET /users/me/notification-settings → returns one entry per type with merged channels + isCustomized flag
  2. Render 30 rows of 4 toggle switches each (in_app / email / push / sms)
  3. PATCH /users/me/notification-settings with the changed items on save
Why polling instead of WebSocket? SSE (Phase 6+) is the upgrade path. For now polling is dead simple, no extra infrastructure, and 60s lag on a notification badge is acceptable for v1. When SSE lands, the FE service swaps the polling loop for a stream — components don't change.

The single entry point producers use. Two methods that everyone calls:

Two design rules every method follows:

1. Owner-scoped queries, 404 not 403

private async findOwnedOrThrow(userId: string, receiptId: string) {
  const receipt = await this.receiptModel.findOne({
    where: { id: receiptId, userId },   // userId always in WHERE
  });
  if (!receipt) {
    // 404 (not 403) — don't leak existence of other users' receipts.
    throw new NotFoundException('Notification not found');
  }
  return receipt;
}

2. Visibility window enforced via JOIN

The bell list and the badge count both join the receipt with the notification, filtering by deliver_at <= now AND (expire_at IS NULL OR expire_at > now). Extracted into a private helper so the two queries can't drift:

private activeNotificationInclude() {
  const now = new Date();
  return {
    model: this.notificationModel,
    required: true,
    where: {
      [Op.and]: [
        { [Op.or]: [{ deliverAt: { [Op.is]: null } }, { deliverAt: { [Op.lte]: now } }] },
        { [Op.or]: [{ expireAt: { [Op.is]: null } },  { expireAt: { [Op.gt]: now } }] },
      ],
    },
  };
}

Code — NotificationPreferenceService

Powers the settings tab. Three operations:

  • getForUser(userId) — returns all 30 types with merged channels + isCustomized
  • bulkUpdate(userId, items[]) — upserts many rows in one transaction
  • resetToDefault(userId, type?) — deletes the override row(s) so defaults take effect
src/modules/notification/services/notification-preference.service.ts (excerpt)
async getForUser(userId: string): Promise<PreferenceView[]> {
  const overrides = await this.preferenceModel.findAll({ where: { userId } });
  const overrideByType = new Map(overrides.map((o) => [o.type, o.channels]));

  const types = Object.keys(NOTIFICATION_DEFAULTS) as NotificationType[];
  return types.map((type) => {
    const override = overrideByType.get(type) ?? null;
    return {
      type,
      channels: resolveChannels(type, override),
      isCustomized: override !== null,
    };
  });
}

Code — DeviceTokenService

Push registration storage. Already supports the future Phase 6 push worker — just no worker reads it yet.

Key design choice: one table for web + mobile, branched on platform:

async register(params: RegisterDeviceParams): Promise<DeviceToken> {
  const tokenString  = this.serializeToken(params.token);
  const endpointHash = this.computeEndpointHash(params.platform, params.token);

  const existing = await this.deviceModel.findOne({
    where: { userId: params.userId, endpointHash },
  });

  if (existing) {
    // Same browser / device → upsert. Re-registration after revoke un-revokes.
    existing.token       = tokenString;
    existing.platform    = params.platform;
    existing.lastSeenAt  = new Date();
    existing.revokedAt   = null;
    await existing.save();
    return existing;
  }

  return this.deviceModel.create({ ...params, tokenString, endpointHash, ... });
}

Code — Generic email template

For Phase 4, every notification email uses one shared template (genericNotificationTemplate):

src/common/email/notification/generic.template.ts
export function genericNotificationTemplate(params: {
  title: string;
  body: string;
  ctaUrl?: string;
  ctaLabel?: string;
}): string {
  const safeTitle = escapeHtml(params.title);
  const safeBody  = escapeHtml(params.body);
  const cta = params.ctaUrl && params.ctaLabel
    ? primaryButton(escapeHtml(params.ctaLabel), params.ctaUrl)
    : '';

  return baseLayout(`
    ${heading(safeTitle)}
    ${paragraph(safeBody)}
    ${cta}
  `, safeTitle);
}
Security rule: every user-controlled string interpolated into HTML must go through escapeHtml(). CLAUDE.md enforces this. The notification system follows it automatically because the template only takes the four fields shown above and escapes them all.

In Phase 6 we can add per-type templates for richer content (e.g. an invoice email with a payment summary table) by mapping NotificationType → templateFn in EmailService.sendNotificationEmail. The generic template stays as the fallback.

Auth + DTO patterns

Every controller in the system follows the same shape:

@ApiTags('Notifications')
@Controller('notifications')
@UseGuards(AuthGuard('jwt'))   // every route requires JWT
export class NotificationController {
  constructor(private readonly receipts: NotificationReceiptService) {}

  @Get()
  @ApiEndpoint(NotificationDocs.list)
  list(
    @Request() req: AuthenticatedRequest,    // req.user.id is the authenticated user
    @Query() query: ListNotificationsDto,    // validated by class-validator
  ) {
    return this.receipts.listForUser(req.user.id, { ...query });
  }
}

Three decorator stacks compose every endpoint:

  • @UseGuards(AuthGuard('jwt')) — checks the bearer token, populates req.user
  • @ApiEndpoint(NotificationDocs.xxx) — adds Swagger metadata (summary, response codes)
  • @Body() / @Query() / @Param() with a DTO class — class-validator runs automatically

For SUPER_ADMIN-only routes (the debug endpoint) we add two more:

@UseGuards(AuthGuard('jwt'), RolesGuard)
@Roles('SUPER_ADMIN')
@Throttle({ default: { limit: 5, ttl: 60_000 } })

What changes in code

NotificationService.deliverToUser() stops calling EmailService directly. Instead:

// Phase 6 sketch
if (channels.email && userEmail) {
  await this.jobs.enqueue('notifications.email_send', {
    to: userEmail,
    title: notification.title,
    body: notification.body,
    ctaUrl,
    ctaLabel,
  }, {
    jobId: `email.${notification.id}.${userId}`,  // idempotency
  });
  delivered.email = 'queued';
}

The worker (separate file) handles the actual send:

@Processor(QueueName.Notifications)
export class EmailSendWorker extends BaseWorker<'notifications.email_send'> {
  async handle(payload, ctx) {
    await this.emailService.sendNotificationEmail(payload);
  }
}

Why this matters

  • Latency drops: notify() returns in 10ms instead of 300–800ms
  • Retries are free: BullMQ retries failed jobs with exponential backoff
  • Visibility: Bull Board UI at /admin/queues shows every job, every failure
  • Scaling: more workers = more throughput, no API code change

Web Push + mobile FCM — Phase 6+ (coming)

How browser push works (the lifecycle)

  1. FE registers a service worker (one-time)
  2. FE asks the browser for push permission
  3. Browser returns a PushSubscription object — a unique URL + crypto keys for that browser/device
  4. FE POSTs the subscription to /devices/register → row in device_token
  5. When we want to send: API calls web-push library with the subscription + payload, signed with our VAPID private key
  6. web-push sends to the browser's push service (FCM for Chrome, Mozilla autopush for FF, Apple for Safari)
  7. Push service wakes up the user's browser → service worker fires → notification banner appears
VAPID = Voluntary Application Server Identification. We generate a public/private keypair once. The public key goes in the FE; the private key stays in our env. Lets browser push services trust our messages without API keys per-provider.

Mobile (Ionic) push via FCM

Ionic apps use Capacitor's PushNotifications plugin which talks to FCM. Same backend code path:

  1. Ionic app calls PushNotifications.register() on first launch
  2. FCM returns a token string
  3. Ionic app POSTs to /devices/register with platform: 'IOS' or 'ANDROID'
  4. Push worker sends to FCM with the token + payload
  5. FCM forwards to APNs (iOS) or directly to the device (Android)

The schema already supports this — device_token.platform is an ENUM with WEB / IOS / ANDROID values, the worker just branches on it.

Real-time — SSE (Phase 6+, coming)

Today the FE polls unread-count every 60 seconds. That's fine for v1 but feels laggy. The fix is Server-Sent Events (SSE) — a one-way stream from server to browser.

How it'll work

// notification.controller.ts (Phase 6+)
@Sse('stream')
stream(@Request() req): Observable<MessageEvent> {
  // Subscribe this user to a Redis pub/sub channel
  return this.realtime.subscribe(req.user.id);
}

When a notification is created:

// in_app_create worker (Phase 6+)
await redisPubSub.publish(`user:${userId}:notifications`, JSON.stringify({
  type: 'notification:created',
  notification: rendered,
}));

The browser's EventSource connection wakes up, the FE updates the signal store, the badge updates instantly.

Glossary

NotificationThe message itself — title + body + data + audience. One row per event.
ReceiptPer-recipient state for a notification. Tracks delivered/viewed/read/clicked/dismissed timestamps.
ChannelHow the notification is delivered: in-app, email, push, sms.
ProducerAny service that calls notify(). Doesn't know or care about channels.
AdapterThe code that talks to a specific channel (Resend for email, web-push for browser push, FCM for mobile).
Fingerprintsha256 dedup key. Same fingerprint within window = no second notification created.
AudienceWho receives the notification: USER (one), GROUP (members), PLATFORM (everyone). Phase 4 only emits USER.
VAPIDVoluntary Application Server Identification — the public/private keypair we use to authenticate Web Push messages.
FCMFirebase Cloud Messaging — Google's push delivery service. Free, used for both Android and iOS (via APNs forwarding).
SSEServer-Sent Events — one-way real-time HTTP stream from server to browser. The right fit for notification badges.
BullMQRedis-backed job queue. Will move email/push/SMS sends off the request path in Phase 6.
Outbox patternFuture: write a job row in the same DB transaction as the domain change, drain to BullMQ post-commit. Solves the "webhook arrives before commit" race.
