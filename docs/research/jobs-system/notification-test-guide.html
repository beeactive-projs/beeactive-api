Hands-on Testing Guide

A guided tour through every notification endpoint. Run these in order — each one builds on the previous. Each step shows the curl command, what to expect back, and the "why" so you understand what's being exercised. Aimed at one person with a terminal + the API running locally.

Prerequisites

  1. Postgres running in Docker (already up — my-postgres)
  2. API running: npm run start:dev in a separate terminal
  3. curl and a working shell (zsh or bash both fine)
  4. Optional: jq for prettier JSON output (brew install jq)

If jq isn't installed, every curl here works as-is — it just prints raw JSON.

Get your tokens

Two seeded accounts you'll use throughout:

RoleEmailPassword
SUPER_ADMINsuperadmin@motionhive.fitTest1234!
USER (recipient)user@motionhive.fitTest1234!

Login as both — the response contains accessToken:

# Login as SUPER_ADMIN
curl -sX POST http://localhost:3800/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"superadmin@motionhive.fit","password":"Test1234!"}'

# Login as the regular user
curl -sX POST http://localhost:3800/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"user@motionhive.fit","password":"Test1234!"}'

Copy the accessToken from each response.

Shell setup (one time)

Set these as shell variables — every step in the guide reuses them. Open a fresh terminal and run:

export BASE="http://localhost:3800"
export ADMIN_TOKEN="paste-the-superadmin-accessToken-here"
export USER_TOKEN="paste-the-user-accessToken-here"
export USER_ID="570ea197-4ac0-4e58-a8c1-bff06c6f945f"      # user@motionhive.fit
export ADMIN_ID="f2ffc358-7c7e-49e7-a9fd-0ab0816ea35f"     # superadmin@motionhive.fit

# Helper: short auth headers
auth_user()  { echo "Authorization: Bearer $USER_TOKEN"; }
auth_admin() { echo "Authorization: Bearer $ADMIN_TOKEN"; }

Tokens expire after a few days — if you start getting 401s, log in again and re-export.

Sanity check

0 API is alive

curl -s "$BASE/health"
Expect: JSON with status: "ok" or similar — anything 2xx means we're good.

Module 1 — Bell basics

Goal: understand the producer → notification → bell loop.

1.1 GET empty unread count

curl -s -H "$(auth_user)" "$BASE/notifications/unread-count"
Expect: {"count":0} (assuming no leftover notifications)
Why: Establishes the baseline. The bell badge in the FE will show this number. Note: even if you have notifications from prior tests, this is fine — just remember the starting count.

1.2 POST fire a notification (admin → user)

curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" \
  -H "Content-Type: application/json" \
  -d '{
    "userId":"'$USER_ID'",
    "type":"INVOICE_PAID",
    "title":"Your first test notification",
    "body":"This is the body. It can be longer text that the bell shows in the dropdown.",
    "data":{"screen":"invoice","entityId":"inv-001"}
  }'
Expect: JSON with notificationId, receiptId, deduped: false, and a delivered object showing each channel's status. inApp and email should both be "sent" (INVOICE_PAID has both enabled by default).
Why: The debug endpoint is the only way to fire a notification through the pipeline before we wire real producers. Same code path a real invoice.service.ts would call. Save the receiptId you get back — you'll use it in 1.4.
Save it: export RID="paste-the-receiptId-here"

1.3 GET see it in the bell

curl -s -H "$(auth_user)" "$BASE/notifications?page=1&limit=10"
Expect: {"items":[{...}],"total":1,"page":1,"pageSize":10} with one entry containing the title/body/data you just sent.
Why: This is what the FE bell dropdown will fetch. Notice the response is a flat shape (joined notification + receipt fields together) — the FE doesn't have to navigate two levels.

1.4 PATCH mark as read

curl -s -o /dev/null -w "HTTP %{http_code}\n" \
  -X PATCH "$BASE/notifications/$RID/read" \
  -H "$(auth_user)"

# Verify the count dropped
curl -s -H "$(auth_user)" "$BASE/notifications/unread-count"
Expect: First call → HTTP 204 (no body). Second call → unread count is one less than before.
Why: The FE will call this when the user clicks a notification. read_at is set to now(); idempotent (calling twice is fine).

Module 2 — Channels & preferences

Goal: understand how the system decides which channels to use per notification type.

2.1 Channel defaults are per-type

Each notification type has different default channels. From notification-defaults.ts:

TypeDefaults
INVOICE_PAIDin_app + email
SESSION_REMINDER_24Hin_app + email + push
SESSION_REMINDER_1Hin_app + push (no email — too late to be useful)
GROUP_MEMBER_JOINEDin_app only (too noisy for email)
PAYMENT_FAILEDin_app + email + push (urgent)
DISPUTE_OPENEDin_app + email + push (deadline-driven)

Try firing different types to see the delivered object change:

curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" -H "Content-Type: application/json" \
  -d '{"userId":"'$USER_ID'","type":"GROUP_MEMBER_JOINED","title":"Group test","body":"x"}'
Expect: email shows "skipped:preference_off" because GROUP_MEMBER_JOINED has email disabled by default.

2.2 GET see your effective preferences

curl -s -H "$(auth_user)" "$BASE/users/me/notification-settings" | head -c 1000
Expect: An array with one entry per known type. Each entry has { type, channels: { in_app, email, push, sms }, isCustomized }. isCustomized is false for all of them right now (no overrides yet).
Why: This is what the FE settings tab will render. It merges system defaults with the user's overrides — you see the effective state per type.

2.3 PATCH override email OFF for INVOICE_PAID

curl -s -X PATCH "$BASE/users/me/notification-settings" \
  -H "$(auth_user)" -H "Content-Type: application/json" \
  -d '{
    "items":[
      {"type":"INVOICE_PAID","channels":{"in_app":true,"email":false,"push":false,"sms":false}}
    ]
  }'
Expect: {"written":1}

2.4 Verify the override took effect

# See your settings — INVOICE_PAID should now show isCustomized: true
curl -s -H "$(auth_user)" "$BASE/users/me/notification-settings" \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print([x for x in d if x['type']=='INVOICE_PAID'])"

# Fire another INVOICE_PAID — email should now skip
curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" -H "Content-Type: application/json" \
  -d '{"userId":"'$USER_ID'","type":"INVOICE_PAID","title":"After override","body":"email should be off now"}'
Expect: The settings show isCustomized: true for INVOICE_PAID. The new notification's email shows "skipped:preference_off".
Why: Sparse override pattern — the DB only stores rows the user has changed. Missing rows fall back to defaults. Means saving "I'm fine with the defaults" is a no-op.

2.5 DELETE reset INVOICE_PAID to default

curl -s -X DELETE "$BASE/users/me/notification-settings/INVOICE_PAID/reset" \
  -H "$(auth_user)"

# Fire again — email should send again
curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" -H "Content-Type: application/json" \
  -d '{"userId":"'$USER_ID'","type":"INVOICE_PAID","title":"After reset","body":"email back on"}'
Expect: {"removed":1}, then the new notification has email: "sent" again.

Module 3 — Dedup & data

3.1 Fingerprint dedup — same key, no second alert

curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" -H "Content-Type: application/json" \
  -d '{"userId":"'$USER_ID'","type":"GROUP_MEMBER_JOINED","title":"Dedup A","body":"first","fingerprint":"my-test-key-1"}'

# Same fingerprint, different title/body — should be ignored
curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" -H "Content-Type: application/json" \
  -d '{"userId":"'$USER_ID'","type":"GROUP_MEMBER_JOINED","title":"Dedup B","body":"second","fingerprint":"my-test-key-1"}'
Expect: First call returns deduped: false. Second call returns deduped: true AND the same notificationId/receiptId as the first.
Why: Producers sometimes fire notify() multiple times for the same logical event (e.g. webhook retried). Fingerprint dedup ensures only one notification reaches the user. Computed as a sha256 of whatever the producer chooses — typically ${eventType}.${entityId}.${date}.

3.2 Severity drives icon + color

curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" -H "Content-Type: application/json" \
  -d '{"userId":"'$USER_ID'","type":"PAYMENT_FAILED","title":"Card declined","body":"Update your card","severity":"error"}'

curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" -H "Content-Type: application/json" \
  -d '{"userId":"'$USER_ID'","type":"INVOICE_PAID","title":"All paid up","body":"Thanks!","severity":"success"}'
Expect: Both succeed. List the bell and you'll see each row with its severity field — the FE will use this to pick an icon (red ✗ for error, green ✓ for success, blue ℹ for info).

3.3 The CTA URL in the email

curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" -H "Content-Type: application/json" \
  -d '{
    "userId":"'$USER_ID'",
    "type":"INVOICE_PAID",
    "title":"Click-through test",
    "body":"Look at the email — it has a button.",
    "data":{"screen":"invoice","entityId":"inv-cta-test"},
    "ctaLabel":"View invoice"
  }'
Expect: If you have RESEND_API_KEY set, an email arrives with a button labeled "View invoice" linking to FRONTEND_URL/invoice/inv-cta-test. If no Resend key, look for the [EMAIL - DEV MODE] log line in the API output.
Why: The CTA URL is built server-side from data.screen + data.entityId + FRONTEND_URL. Producers don't need to know the FE routing structure — they just say "this is about screen X, entity Y" and the email worker knows how to compose the link.

Module 4 — The funnel timestamps

Each receipt has 5 timestamps that progress through the user-engagement funnel. Let's exercise each one.

4.1 Inspect the funnel state in DB

The FE will work with the API responses, but it's helpful to see the underlying DB rows once. Open a new terminal:

docker exec -it my-postgres psql -U postgres -d beeactive -c "
  SELECT id, delivered_at, viewed_at, read_at, clicked_at, dismissed_at
  FROM notification_receipt
  WHERE user_id = '$USER_ID'
  ORDER BY created_at DESC LIMIT 5;
"
Why: All 5 timestamps start NULL except delivered_at (set when the receipt is created). The other 4 fill in as the user interacts with the notification.

4.2 PATCH mark a batch as viewed

Get a few recent receipt IDs first:

curl -s -H "$(auth_user)" "$BASE/notifications?limit=3" \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print(','.join(['\"' + i['id'] + '\"' for i in d['items']]))"

Then mark them viewed (replace the IDs with what you got back):

curl -s -X PATCH "$BASE/notifications/viewed" \
  -H "$(auth_user)" -H "Content-Type: application/json" \
  -d '{"ids":["id-1","id-2","id-3"]}'
Expect: {"updated":3} (or fewer if some were already viewed).
Why: When the FE bell dropdown opens, it sends the IDs of all visible notifications to mark them viewed — but NOT read. This gives us analytics ("X% of notifications get viewed but not clicked") without changing the unread badge.

4.3 PATCH mark as clicked (sets clicked + read in one shot)

curl -s -o /dev/null -w "HTTP %{http_code}\n" \
  -X PATCH "$BASE/notifications/$RID/clicked" \
  -H "$(auth_user)"
Expect: HTTP 204. Re-query the DB row — both clicked_at and read_at are now set.
Why: When the user clicks the notification's CTA, the FE calls this endpoint AND navigates to the deep link. We set both timestamps in one save — clicking implies reading.

4.4 PATCH dismiss (X-out without reading)

curl -s -o /dev/null -w "HTTP %{http_code}\n" \
  -X PATCH "$BASE/notifications/$RID/dismiss" \
  -H "$(auth_user)"
Expect: HTTP 204. The notification is filtered out of the unread count and (when unreadOnly=true) the list.
Why: Some users want to clear notifications without "reading" them — the X button. Tracking this separately from read lets us see if certain notification types get dismissed a lot (signal that the user doesn't find them useful).

Module 5 — List behavior

5.1 Pagination

# First, fire ~5 notifications so we have content
for i in 1 2 3 4 5; do
  curl -s -X POST "$BASE/admin/debug/notify" \
    -H "$(auth_admin)" -H "Content-Type: application/json" \
    -d "{\"userId\":\"$USER_ID\",\"type\":\"GROUP_MEMBER_JOINED\",\"title\":\"Page $i\",\"body\":\"Test $i\"}" \
    -o /dev/null
done

# Page 1, 2 per page
curl -s -H "$(auth_user)" "$BASE/notifications?page=1&limit=2"
echo ""
# Page 2, 2 per page
curl -s -H "$(auth_user)" "$BASE/notifications?page=2&limit=2"
Expect: Each response has { items: [2 entries], total: N, page, pageSize }. Different items in page 1 vs page 2.
Note: limit is capped at 100 (try ?limit=999 to see the 400 error).

5.2 unreadOnly=true filter

# With unread-only: only items where read_at IS NULL AND dismissed_at IS NULL
curl -s -H "$(auth_user)" "$BASE/notifications?unreadOnly=true&limit=20"

# Without: everything visible
curl -s -H "$(auth_user)" "$BASE/notifications?limit=20"
Expect: The first call returns fewer items than the second — the dismissed/read ones are filtered out.

5.3 PATCH mark all as read

curl -s -X PATCH "$BASE/notifications/read-all" -H "$(auth_user)"
curl -s -H "$(auth_user)" "$BASE/notifications/unread-count"
Expect: {"updated":N} followed by {"count":0}.

Module 6 — Devices

The push worker doesn't exist yet (Phase 6+), but the registration endpoints do. Let's test the storage.

6.1 POST register a fake Web Push subscription

curl -s -X POST "$BASE/devices/register" \
  -H "$(auth_user)" -H "Content-Type: application/json" \
  -d '{
    "platform":"WEB",
    "subscription":{
      "endpoint":"https://fcm.googleapis.com/fcm/send/test-chrome-001",
      "keys":{"p256dh":"BKx-fake-public-key-for-testing","auth":"fake-auth-secret"}
    },
    "deviceLabel":"Chrome on Mac"
  }'
Expect: A device row with platform: "WEB", token being the JSON-stringified subscription, endpointHash being a 64-char sha256.
Why: In production, the FE will get a real subscription from navigator.serviceWorker.pushManager.subscribe() and send it here. The schema accepts both formats (object for WEB, string for FCM).

6.2 POST register a fake iOS device (FCM token)

curl -s -X POST "$BASE/devices/register" \
  -H "$(auth_user)" -H "Content-Type: application/json" \
  -d '{
    "platform":"IOS",
    "tokenString":"fake-fcm-token-for-iphone-1234567890",
    "deviceLabel":"iPhone 15"
  }'
Expect: Another device row, platform: "IOS", token is the raw FCM string.

Now list — you should see both devices:

curl -s -H "$(auth_user)" "$BASE/devices"

6.3 Same device twice → upsert (idempotent)

# Run the WEB registration from 6.1 again — same endpoint URL
curl -s -X POST "$BASE/devices/register" \
  -H "$(auth_user)" -H "Content-Type: application/json" \
  -d '{
    "platform":"WEB",
    "subscription":{
      "endpoint":"https://fcm.googleapis.com/fcm/send/test-chrome-001",
      "keys":{"p256dh":"new-key-after-rotation","auth":"new-auth"}
    },
    "deviceLabel":"Chrome on Mac (updated)"
  }'

# List — should still be 2 devices, not 3. The first one was updated in place.
curl -s -H "$(auth_user)" "$BASE/devices" | python3 -c "import sys,json; print(f'Count: {len(json.load(sys.stdin))}')"
Expect: Count: 2. Looking at the WEB device, the deviceLabel and token reflect the new values.
Why: Browsers can rotate subscription keys. Same device → upsert by endpoint_hash, bump last_seen_at. No duplicates.

6.4 Heartbeat + revoke

Get the WEB device ID, then exercise heartbeat + revoke:

export DEV_ID=$(curl -s -H "$(auth_user)" "$BASE/devices" \
  | python3 -c "import sys,json; print([d['id'] for d in json.load(sys.stdin) if d['platform']=='WEB'][0])")

# Heartbeat — bumps last_seen_at
curl -s -o /dev/null -w "Heartbeat: HTTP %{http_code}\n" \
  -X PATCH "$BASE/devices/$DEV_ID/seen" -H "$(auth_user)"

# Revoke — sets revoked_at
curl -s -o /dev/null -w "Revoke: HTTP %{http_code}\n" \
  -X DELETE "$BASE/devices/$DEV_ID" -H "$(auth_user)"

# List — WEB should be gone (revoked filter), IOS still there
curl -s -H "$(auth_user)" "$BASE/devices"
Expect: Both calls return HTTP 204. Final list shows only the IOS device.

Module 7 — Security & validation

7.1 Without a JWT → 401

curl -s -o /dev/null -w "HTTP %{http_code}\n" "$BASE/notifications/unread-count"
Expect: HTTP 401

7.2 Other user's receipt → 404 (not 403)

# Get a receipt belonging to user@
export RID=$(curl -s -H "$(auth_user)" "$BASE/notifications?limit=1" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['items'][0]['id'])")

# Admin tries to mark it read — 404, not 403
curl -s -o /dev/null -w "HTTP %{http_code}\n" \
  -X PATCH "$BASE/notifications/$RID/read" -H "$(auth_admin)"
Expect: HTTP 404
Why: 403 would tell the attacker "this resource exists but you can't access it" — leaks information. 404 says "doesn't exist for you" — same response as if the ID was random garbage.

7.3 Non-admin trying the debug endpoint → 403

curl -s -o /dev/null -w "HTTP %{http_code}\n" \
  -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_user)" -H "Content-Type: application/json" \
  -d '{"userId":"'$USER_ID'","type":"INVOICE_PAID","title":"x","body":"x"}'
Expect: HTTP 403 — RolesGuard rejects.

7.4 Validation kicks in

# Bad type
curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" -H "Content-Type: application/json" \
  -d '{"userId":"'$USER_ID'","type":"NOT_A_REAL_TYPE","title":"x","body":"y"}'

# Bad UUID for userId
curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" -H "Content-Type: application/json" \
  -d '{"userId":"not-a-uuid","type":"INVOICE_PAID","title":"x","body":"y"}'

# Bad enum on settings reset
curl -s -X DELETE "$BASE/users/me/notification-settings/FAKE_TYPE/reset" \
  -H "$(auth_user)"

# Body too long (the title cap is 200)
curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" -H "Content-Type: application/json" \
  -d "{\"userId\":\"$USER_ID\",\"type\":\"INVOICE_PAID\",\"title\":\"$(printf 'A%.0s' {1..300})\",\"body\":\"x\"}"
Expect: All return HTTP 400 with a message array explaining what's wrong.

7.5 Throttler kicks in

The debug endpoint is throttled at 5 calls per minute. Run it 6 times rapidly:

for i in 1 2 3 4 5 6 7; do
  curl -s -o /dev/null -w "Call $i: HTTP %{http_code}\n" \
    -X POST "$BASE/admin/debug/notify" \
    -H "$(auth_admin)" -H "Content-Type: application/json" \
    -d "{\"userId\":\"$USER_ID\",\"type\":\"INVOICE_PAID\",\"title\":\"Throttle $i\",\"body\":\"x\",\"fingerprint\":\"throttle-$i\"}"
done
Expect: First 5 calls return 201; calls 6 and 7 return 429 (Too Many Requests). Wait 60s and you can call again.

Module 8 — Edge cases

8.1 Notification scheduled for the future

The debug endpoint doesn't expose deliver_at, so we'll set it directly in the DB:

# 1. Create a normal notification
NOTIF=$(curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" -H "Content-Type: application/json" \
  -d "{\"userId\":\"$USER_ID\",\"type\":\"INVOICE_PAID\",\"title\":\"Future delivery\",\"body\":\"shouldn't show yet\"}")
NID=$(echo "$NOTIF" | python3 -c "import sys,json; print(json.load(sys.stdin)['notificationId'])")

# 2. Push its deliver_at to 1 hour in the future
docker exec -it my-postgres psql -U postgres -d beeactive -c \
  "UPDATE notification SET deliver_at = NOW() + INTERVAL '1 hour' WHERE id = '$NID';"

# 3. List — this notification should NOT appear
curl -s -H "$(auth_user)" "$BASE/notifications?limit=20" \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print('Future notif present:', any(i['notificationId']=='$NID' for i in d['items']))"
Expect: Future notif present: False — the JOIN filter excludes notifications with deliver_at > now.
Why: Lets producers schedule notifications in advance ("session reminder at 9am tomorrow"). The bell only shows what's currently due.

8.2 Expired notification disappears

NOTIF=$(curl -s -X POST "$BASE/admin/debug/notify" \
  -H "$(auth_admin)" -H "Content-Type: application/json" \
  -d "{\"userId\":\"$USER_ID\",\"type\":\"GROUP_MEMBER_JOINED\",\"title\":\"Expiring\",\"body\":\"x\"}")
NID=$(echo "$NOTIF" | python3 -c "import sys,json; print(json.load(sys.stdin)['notificationId'])")

# Set expire_at in the past
docker exec -it my-postgres psql -U postgres -d beeactive -c \
  "UPDATE notification SET expire_at = NOW() - INTERVAL '1 day' WHERE id = '$NID';"

curl -s -H "$(auth_user)" "$BASE/notifications?limit=20" \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print('Expired notif present:', any(i['notificationId']=='$NID' for i in d['items']))"
Expect: Expired notif present: False — the row is still in the DB but the bell skips it.

8.3 Email failure is recorded, in-app still works

Hard to simulate a Resend failure without messing with the env, but you can verify the audit field works by inspecting delivered_channels after a normal send:

docker exec -it my-postgres psql -U postgres -d beeactive -c \
  "SELECT delivered_channels FROM notification_receipt WHERE user_id = '$USER_ID' ORDER BY created_at DESC LIMIT 5;"
Expect: Each row has the JSONB audit. Successful sends show {"email":"sent",...}. Failed ones would show {"email":"failed:<reason>",...}.
Why: When a user complains "I didn't get the email", check this field. "sent" = problem is on Resend's side or their inbox. "failed:..." = we know why. "skipped:preference_off" = they turned it off themselves.

8.4 Reset all preferences at once

# Make some overrides first
curl -s -X PATCH "$BASE/users/me/notification-settings" \
  -H "$(auth_user)" -H "Content-Type: application/json" \
  -d '{"items":[
    {"type":"INVOICE_PAID","channels":{"email":false}},
    {"type":"GROUP_MEMBER_JOINED","channels":{"in_app":false}}
  ]}'

# Wipe them all in one shot
curl -s -X DELETE "$BASE/users/me/notification-settings" -H "$(auth_user)"

# Verify isCustomized = false everywhere
curl -s -H "$(auth_user)" "$BASE/users/me/notification-settings" \
  | python3 -c "import sys,json; d=json.load(sys.stdin); print('Customized count:', sum(1 for x in d if x['isCustomized']))"
Expect: {"removed":2} then Customized count: 0.

Cleanup commands

If you want to wipe your test data and start over:

# Delete all notifications + receipts you've created
docker exec -it my-postgres psql -U postgres -d beeactive -c "
  DELETE FROM notification_receipt WHERE user_id = '570ea197-4ac0-4e58-a8c1-bff06c6f945f';
  DELETE FROM notification WHERE id NOT IN (SELECT DISTINCT notification_id FROM notification_receipt);
"

# Delete all preference overrides
docker exec -it my-postgres psql -U postgres -d beeactive -c \
  "DELETE FROM notification_preference WHERE user_id = '570ea197-4ac0-4e58-a8c1-bff06c6f945f';"

# Delete all device tokens
docker exec -it my-postgres psql -U postgres -d beeactive -c \
  "DELETE FROM device_token WHERE user_id = '570ea197-4ac0-4e58-a8c1-bff06c6f945f';"

# Verify clean state
curl -s -H "$(auth_user)" "$BASE/notifications/unread-count"
curl -s -H "$(auth_user)" "$BASE/devices"
