1. TypeScript basics

TypeScript is JavaScript with types. The compiler checks at build-time that you're not accidentally passing a string where a number is expected. At runtime, everything becomes regular JavaScript.

Things you'll see in this codebase

Type annotations

// `name` must be a string. `age` must be a number. Returns a string.
function greet(name: string, age: number): string {
  return `Hi ${name}, you are ${age}.`;
}

// `findById` returns a `User` OR `null` (the `| null` is a union).
async function findById(id: string): Promise<User | null> {
  return userModel.findByPk(id);
}

Interfaces & types

// An interface describes the shape of an object.
interface NotifyParams {
  userId: string;
  type: NotificationType;
  title: string;
  body: string;
  data?: NotificationData;   // ?: means optional
}

// `type` is similar but more flexible. Used for unions:
type SocialProvider = 'GOOGLE' | 'FACEBOOK' | 'APPLE';

Classes

class GroupService {
  // `private readonly` = this field can only be assigned in the
  // constructor, and only this class can read it.
  constructor(private readonly groupModel: typeof Group) {}

  async findById(id: string): Promise<Group | null> {
    return this.groupModel.findByPk(id);
  }
}

Generics

// `T` is a placeholder for whatever type the caller passes.
// This lets the same function work with User, Group, anything.
function buildPaginatedResponse<T>(
  items: T[],
  total: number,
  page: number,
  pageSize: number,
): PaginatedResponse<T> {
  return { items, total, page, pageSize };
}

// Usage:
const result = buildPaginatedResponse<User>(users, 100, 1, 20);

async / await

Anything that hits a database, the network, or a file is asynchronous — it returns a Promise. await pauses the function until the Promise resolves. 

// `await` only works inside an `async` function.
async function loadUser(id: string) {
  const user = await userModel.findByPk(id);  // pause until DB returns
  console.log(user.email);                    // runs after
}

2. NestJS in 5 minutes

NestJS is a framework for building server-side TypeScript apps. Think of it as the structure layer that organizes Express into modules, controllers, and services. 

HTTP Request
     │
     ▼
┌───────────────┐    ┌──────────────┐    ┌───────────────┐    ┌──────────┐
│  Controller   │───▶│   Service    │───▶│  Sequelize    │───▶│ Postgres │
│ (HTTP layer)  │    │ (business    │    │   (ORM)       │    │   (DB)   │
│               │    │  logic)      │    │               │    │          │
└───────────────┘    └──────────────┘    └───────────────┘    └──────────┘
     ▲
     │ HTTP Response

The three building blocks

Block File suffix Job
Controller *.controller.ts Receive HTTP request, validate input, call a service, return a response. Should be small.
Service *.service.ts Business logic. Talks to the database. Reusable.
Module *.module.ts Wires controllers + services + dependencies together so NestJS knows what depends on what.

Bootstrap

src/main.ts
async function bootstrap() {
  const app = await NestFactory.create(AppModule);

  // Apply security middleware
  app.use(helmet());

  // Validate every DTO on every request
  app.useGlobalPipes(new ValidationPipe({ whitelist: true, transform: true }));

  // Catch every exception, format the response
  app.useGlobalFilters(new HttpExceptionFilter());

  await app.listen(3000);
}
bootstrap();

AppModule is the root — it imports every feature module (User, Group, Payment, etc.) and the global infrastructure (database, JWT, throttling).

3. Dependency injection (DI)

DI is the single biggest concept in NestJS. It says: don't create your own dependencies; ask for them.

Without DI (don't do this)

// Tightly coupled — UserService creates its own EmailService.
class UserService {
  private emailService = new EmailService(new ConfigService());

  async register(email: string) {
    // ...
    this.emailService.sendWelcome(email);
  }
}

Problem: when you write a test for UserService.register, you can't swap EmailService for a fake one.

With DI (the NestJS way)

@Injectable()
class UserService {
  // NestJS will create the EmailService and pass it in.
  constructor(private readonly emailService: EmailService) {}

  async register(email: string) {
    // ...
    this.emailService.sendWelcome(email);
  }
}

At startup, NestJS reads every @Injectable() class, looks at what each constructor needs, and builds a graph of who depends on what. It then constructs everything in the right order. In tests, you can swap any provider with { provide: EmailService, useValue: fakeEmail }.

The four parts of DI

  1. Provider — a class marked @Injectable(). Examples: services, repositories.
  2. Module — declares which providers it owns and which ones it exports for other modules to use.
  3. Consumer — any class with a constructor that asks for a provider.
  4. Container — NestJS itself, which builds the graph and creates instances.

Real example — GroupService

src/modules/group/group.service.ts
@Injectable()
export class GroupService {
  constructor(
    @InjectModel(Group)
    private readonly groupModel: typeof Group,
    @InjectModel(GroupMember)
    private readonly memberModel: typeof GroupMember,
    @InjectModel(GroupJoinRequest)
    private readonly joinRequestModel: typeof GroupJoinRequest,
    @InjectModel(InstructorClient)
    private readonly instructorClientModel: typeof InstructorClient,
    @InjectModel(User)
    private readonly userModel: typeof User,
    private readonly emailService: EmailService,
    private readonly cryptoService: CryptoService,
    @Inject(WINSTON_MODULE_NEST_PROVIDER)
    private readonly logger: LoggerService,
    private readonly searchIndexService: SearchIndexService,
    private readonly notificationService: NotificationService,
  ) {}
}

Every line in the constructor says: "I need a thing of this type." NestJS finds it and passes it in. The class never calls new EmailService(...).

4. Decorators (the @ symbols)

A decorator is a function prefixed with @ that attaches metadata to a class, method, or parameter. NestJS reads that metadata at startup to wire everything.

The big ones you'll see daily

Decorator Where What it says
@Module({...}) Module class "This is a module. Here are its imports/providers/controllers."
@Injectable() Service class "NestJS may instantiate me and inject my deps."
@Controller('groups') Controller class "All my routes start with /groups."
@Get('/:id') Method "This method handles GET /groups/:id."
@Param('id', ParseUUIDPipe) Param "Bind :id here, and validate it's a UUID."
@Body() Param "Bind the request body here (must be a DTO)."
@Query() Param "Bind the URL query string here."
@Request() Param "Bind the raw Express request (gives access to req.user)."
@UseGuards(AuthGuard('jwt'), RolesGuard) Method or class "Require a JWT and check the @Roles list."
@Roles('INSTRUCTOR') Method "Only INSTRUCTOR / ADMIN / SUPER_ADMIN may call this."
@InjectModel(User) Constructor param "Inject the Sequelize repository for User."
@Inject(SOME_TOKEN) Constructor param "Inject the provider registered under this token (used for non-class providers)."

How decorators look in practice

src/modules/group/group.controller.ts
@ApiTags('Groups')                     // groups all routes under "Groups" in Swagger
@Controller('groups')                  // routes start with /groups
export class GroupController {
  constructor(private readonly groupService: GroupService) {}

  @Get(':id')                          // GET /groups/:id
  @UseGuards(AuthGuard('jwt'))         // require login
  @ApiEndpoint(GroupDocs.getById)      // Swagger docs from common/docs/group.docs.ts
  async getById(
    @Param('id', ParseUUIDPipe) id: string,
    @Request() req: AuthenticatedRequest,
  ) {
    return this.groupService.getById(id, req.user.id);
  }
}

What does SequelizeModule.forFeature(...) do?

It tells the Sequelize DI integration: "for this module, expose repositories for these entities." After this, any service in this module can do @InjectModel(Group) in its constructor and get a typed reference to the Group model.

3. The service

The service holds the business logic. It's where the interesting decisions happen.

src/modules/group/group.service.ts (excerpt)
@Injectable()
export class GroupService {
  constructor(
    @InjectModel(Group) private readonly groupModel: typeof Group,
    // ... other models + services ...
    private readonly notificationService: NotificationService,
  ) {}

  async transferOwnership(groupId: string, currentOwnerId: string, newOwnerId: string) {
    const group = await this.assertOwnerAndGet(groupId, currentOwnerId);
    if (currentOwnerId === newOwnerId) {
      throw new BadRequestException('You are already the owner');
    }
    // ... role flip + group update inside a tx ...

    // Fire notifications AFTER the tx commits.
    const groupRef = { id: group.id, name: group.name };
    await Promise.all([
      this.notificationService
        .notify(groupOwnershipTransferredToNewOwner(newOwnerId, groupRef))
        .catch((err) => this.logger.error(...)),
      this.notificationService
        .notify(groupOwnershipTransferredFromOldOwner(currentOwnerId, groupRef))
        .catch((err) => this.logger.error(...)),
    ]);

    return { message: 'Ownership transferred successfully' };
  }
}

8. Authentication & authorization

JWT-based auth

On login, AuthService.login() issues an access token (short-lived, ~15 min) and a refresh token (longer-lived, stored in DB so we can revoke). The FE sends the access token on every request as Authorization: Bearer <token>. 

1. POST /auth/login { email, password }
       │
       ▼
   AuthService.login()
       │ ├── verify password
       │ ├── reset failed-attempt counter
       │ ├── generate access + refresh tokens
       │ └── store refresh in DB
       ▼
   { accessToken, refreshToken, user }

2. Future requests:
   GET /groups/abc
   Authorization: Bearer eyJhbGciOi...
       │
       ▼
   AuthGuard('jwt') decodes the token and populates req.user.
       │
       ▼
   Controller sees req.user.id and proceeds.

9. Database (Sequelize)

We use Sequelize as our ORM (Object-Relational Mapper). Sequelize lets us write TypeScript classes that map to SQL tables, and call methods like .findByPk(id) instead of writing raw SQL.

Reading data

// Single row by primary key
const user = await this.userModel.findByPk(userId);

// First match
const user = await this.userModel.findOne({ where: { email } });

// All matches
const groups = await this.groupModel.findAll({
  where: { instructorId, isPublic: true },
  order: [['createdAt', 'DESC']],
  limit: 20,
});

// With a join (eager loading)
const sub = await this.subscriptionModel.findByPk(id, {
  include: [
    { model: Product, attributes: ['id', 'name'] },
    { model: User, as: 'client', attributes: ['id', 'firstName', 'lastName'] },
  ],
});

Writing data

// Create
const group = await this.groupModel.create({
  name: 'Yoga',
  instructorId: userId,
});

// Update an existing instance
group.name = 'Yoga Wednesdays';
await group.save();

// Update via static method
await this.groupModel.update(
  { name: 'New name' },
  { where: { id: groupId } },
);

// Soft delete (paranoid mode)
await group.destroy();    // sets deleted_at; row is hidden from default queries
await group.restore();    // unsets deleted_at

Naming convention

underscored: true on every entity means the DB columns are snake_case, but the TS fields are camelCase.

TypeScript Database column
instructorId instructor_id
createdAt created_at
isEmailVerified is_email_verified

10. Transactions

A transaction is a way to say "either ALL these DB writes succeed, or NONE of them do." If one fails, the others are rolled back.

Why we need them

Suppose accepting an invitation does three things: add a group member, assign a role, and mark the invitation accepted. If the role-assignment fails after the member is added, we'd have an orphaned member with no role. A transaction prevents that.

The pattern

const transaction = await this.sequelize.transaction();
try {
  // EVERY ORM call inside MUST pass { transaction }
  await this.groupService.addMember(groupId, userId, transaction);
  await this.roleService.assignRoleToUser(userId, roleId, ..., transaction);
  await invitation.update({ acceptedAt: new Date() }, { transaction });

  await transaction.commit();        // ✓ all good, persist everything
} catch (error) {
  await transaction.rollback();      // ✗ undo all writes
  throw error;
}
Common bug: forgetting to pass { transaction } on an inner call. That call commits to the default DB connection instead of the transaction — and the rollback can't undo it. EVERY ORM call inside a tx callback must pass the tx.

Side effects after commit

Notifications, emails, Cloudinary uploads — these are NOT part of the DB transaction. If you fire them inside the try block and the tx rolls back, you've sent a "payment received" email for a payment that didn't actually finalize.

Always fire side effects after tx.commit() succeeds.

11. Notification system

Every user-facing event in the app (invoice paid, group invitation received, post approved) flows through one notification system. The producer (some service) calls a builder, which returns a NotifyParams object, which is passed to NotificationService.notify(). 

Producer (service method)
       │
       │  invoiceCreatedForClient(clientId, invoice)
       ▼
┌────────────────────────────────┐
│  Builder                       │  returns NotifyParams
│  (payment/notifications.ts)    │  { userId, type, title, body, data }
└────────────────────────────────┘
       │
       ▼
┌────────────────────────────────┐
│  notificationService.notify()  │
│  • Resolves user preferences   │
│  • Writes notification row     │
│  • Writes receipt row          │
│  • Enqueues email job (BullMQ) │
└────────────────────────────────┘
       │
       ├──▶ In-app: bell shows it on next /notifications poll
       │
       └──▶ Email: BullMQ worker sends via Resend

Domain model

Table Purpose
notification One row per event. Stores type, title, body, data.
notification_receipt One row per (notification, recipient). Tracks viewed/read/dismissed/delivered_channels.
notification_preference Per-user, per-category channel preferences (email on/off etc.).
device_token Phase 3: push notification tokens.

For a 1:1 notification (invoice paid → instructor): one notification row + one notification_receipt. For a broadcast (post approved in a group → 50 members): one notification row + 50 notification_receipt rows.

The builder pattern

Producers don't write notification objects inline. They call a builder co-located with their domain.

src/modules/payment/notifications.ts (excerpt)
export function invoiceCreatedForClient(
  clientId: string,
  invoice: InvoiceForBuilder,

  const amount = formatMoney(invoice.amountDueCents, invoice.currency);
  const due = formatDueDate(invoice.dueDate);
  return {
    userId: clientId,
    type: NotificationType.INVOICE_CREATED,
    title: 'New invoice',
    body: due ? `${amount} due ${due}.` : `${amount} — open to view details.`,
    data: { screen: 'profile/invoices', entityId: invoice.id },
  };
}

The Outbox — for webhook flows

Stripe webhook handlers run inside a transaction owned by the dispatcher. If we fire notify() inside that tx and the tx rolls back, the notification still persists — meaning the user gets a "payment received" email for a payment that didn't actually finalize.

Solution: NotificationOutbox. The dispatcher creates one, hands it to handlers, and flushes it AFTER the tx commits.

src/modules/notification/notification-outbox.ts
export class NotificationOutbox {
  private readonly pending: NotifyParams[] = [];

  add(params: NotifyParams): void { this.pending.push(params); }
  discard(): void { this.pending.length = 0; }

  async flush(): Promise<void> {
    const items = [...this.pending];
    this.pending.length = 0;
    for (const params of items) {
      try { await this.notifications.notify(params); }
      catch (err) { /* log, don't throw */ }
    }
  }
}
src/modules/payment/services/webhook-handler.service.ts (excerpt)
const outbox = new NotificationOutbox(this.notificationService, this.logger);
try {
  await this.sequelize.transaction(async (tx) => {
    await this.dispatchHandler(event, tx, outbox);   // handlers call outbox.add(...)
    auditRow.status = WebhookEventStatus.PROCESSED;
    await auditRow.save({ transaction: tx });
  });
  await outbox.flush();      // ✓ tx committed — fire all queued notifies
} catch (err) {
  outbox.discard();          // ✗ tx rolled back — drop them
  // ... handle error ...
}

12. Jobs system (BullMQ)

Why jobs? Some work shouldn't happen during the HTTP request. Sending an email takes 200-500ms — making the user wait feels slow. Email failure should not 500 the request. So we put it on a queue and a worker handles it asynchronously.

The pieces

┌──────────────────────────────────────────────────────────────────────┐
│  Producer                  Queue (Redis)              Worker          │
│  ─────────                 ─────────────              ──────          │
│                                                                       │
│  service.notify(...)                                                  │
│     │                                                                 │
│     │ enqueue                                                         │
│     ▼                                                                 │
│  ┌─────────┐    BullMQ    ┌───────────────┐    pull     ┌──────────┐ │

1. The Queue (Redis-backed)

BullMQ stores jobs in Redis. Each queue has a name (e.g. notifications) and default settings (retries, backoff).

src/modules/jobs/job-registry.ts
export enum QueueName {
  Notifications = 'notifications',
}

export const QUEUE_DEFAULTS = {
  [QueueName.Notifications]: {
    defaultJobOptions: {
      attempts: 5,                         // retry up to 5 times
      backoff: { type: 'exponential', delay: 5000 },
      removeOnComplete: { age: 86400 },    // keep done jobs 24h
      removeOnFail: { age: 7 * 86400 },    // keep failed jobs 7d
    },
  },
};

2. The Producer (JobsService)

The producer enqueues a job. It doesn't wait for the worker.

src/modules/jobs/jobs.service.ts (excerpt)
@Injectable()
export class JobsService {
  constructor(
    @InjectQueue(QueueName.Notifications)
    private readonly notificationsQueue: Queue,
  ) {}

  async enqueue<K extends keyof JobPayloadMap>(
    name: K,
    payload: JobPayloadMap[K],
    opts?: { jobId?: string },
  ) {
    return this.notificationsQueue.add(name, payload, {
      jobId: opts?.jobId,         // ← idempotency: same jobId = same job
    });
  }
}

3. The Worker (consumer)

A worker is a class decorated with @Processor(queueName) and extending BaseWorker. It implements handle(payload, ctx).

src/modules/jobs/workers/notifications/email-send.worker.ts
@Processor(QueueName.Notifications)
export class EmailSendWorker extends BaseWorker<'notifications.email_send'> {
  constructor(
    @Inject(WINSTON_MODULE_NEST_PROVIDER) logger: LoggerService,
    private readonly emailService: EmailService,
    private readonly receiptService: NotificationReceiptService,
  ) {
    super(logger);
  }

  async handle(
    payload: JobPayload<'notifications.email_send'>,
    ctx: JobContext,
  ): Promise<void> {
    // 1. Idempotency check — already delivered? skip.
    if (await this.receiptService.isChannelDelivered(payload.receiptId, 'email')) {
      ctx.log.log(`email skip (already delivered)`);
      return;
    }

    // 2. Send via Resend
    const status = await this.emailService.sendNotificationEmail({
      to: payload.to,
      title: payload.title,
      body: payload.body,
      ctaUrl: payload.ctaUrl,
    });

    // 3. Record outcome on the receipt row
    if (status.ok) {
      await this.receiptService.recordChannelOutcome(payload.receiptId, 'email', 'sent');
      return;
    }

    // 4. On failure, record + throw so BullMQ retries
    await this.receiptService.recordChannelOutcome(
      payload.receiptId, 'email', `failed:${status.reason}`
    );
    throw new TemporaryError(`resend send failed: ${status.reason}`);
  }
}

4. End-to-end flow for an email notification

1. invoice.service.ts:
   await notificationService.notify(invoiceCreatedForClient(...))

2. notification.service.ts:
   • Resolve preferences (email channel ON for INVOICE_CREATED)
   • INSERT INTO notification (...)
   • INSERT INTO notification_receipt (...)
   • SET delivered_channels.in_app = 'sent'  ← in-app delivery is sync
   • SET delivered_channels.email = 'queued' ← email is async
   • jobsService.enqueue('notifications.email_send', { receiptId, to, title, body, ctaUrl })

3. BullMQ:
   • Job lands in Redis
   • EmailSendWorker pulls it (in-process, same Node)

4. EmailSendWorker.handle():
   • Check isChannelDelivered (idempotency)
   • Call Resend HTTP API
   • UPDATE notification_receipt SET delivered_channels.email = 'sent'

5. User opens the FE bell:
   • GET /notifications returns the row with delivered_channels for audit
   • User sees "Invoice paid" in the dropdown

Idempotency — two layers

Layer What it covers
BullMQ jobId If the same job is enqueued twice (e.g. retry of a failed producer), Redis deduplicates by jobId.
receiptService.isChannelDelivered If a worker retries after a transient failure, the second attempt sees the receipt is already marked 'sent' and skips.

Both are needed because Resend has no idempotency-key support.

BullMQ retry semantics

  • throw new TemporaryError(...) → BullMQ retries with exponential backoff (5 attempts default).
  • throw new PermanentError(...) → wrapped in UnrecoverableError; BullMQ stops retrying immediately.
  • return normally → job marked complete.

13. Stripe webhooks

Stripe sends HTTP POSTs to /webhooks/stripe when events happen (invoice paid, refund issued, account onboarded). We MUST verify the signature and respond 2xx within 20s, or Stripe retries.

The dispatcher

1. POST /webhooks/stripe (raw body, Stripe-Signature header)
       │
       ▼
2. WebhookHandlerService.handleIncomingEvent()
       │ ├── verify signature (Stripe SDK)
       │ ├── INSERT INTO webhook_event (idempotent — UNIQUE on stripe_event_id)
       │ │     ↳ if duplicate: respond 200, no work
       │ └── if event type is not in handledEventTypes: stamp IGNORED, respond 200
       ▼
3. Open a Sequelize transaction
       │
       │  Create a NotificationOutbox (notify-after-commit safety)
       │
       ▼
4. dispatchHandler(event, tx, outbox)
       │  Routes to the right service:
       │   - account.updated         → connectService.syncAccountFromWebhook
       │   - invoice.paid            → invoiceService.syncFromStripeInvoice
       │   - invoice.payment_failed  → invoiceService.handlePaymentFailed
       │   - charge.refunded         → refundService.syncRefundFromWebhook
       │   - customer.subscription.* → subscriptionService.syncFromWebhook
       │
       ▼
5. tx.commit()  ✓
       │
       ▼
6. outbox.flush()  → fires queued notifications
       │
       ▼
7. Respond 200 to Stripe

Idempotency: the webhook_event table

// migrations/.../*.sql
CREATE TABLE webhook_event (
  id CHAR(36) PRIMARY KEY,
  stripe_event_id VARCHAR(255) NOT NULL,
  type VARCHAR(255) NOT NULL,
  status webhook_event_status NOT NULL,
  ...
  CONSTRAINT uk_webhook_event_id UNIQUE (stripe_event_id)
);

On every incoming event we try INSERT. The UNIQUE constraint catches duplicates — the dispatcher catches the UniqueConstraintError and responds with the existing row's status, so Stripe doesn't retry-spam us.

Why raw body matters

Stripe signs the exact byte stream. If Express's JSON parser re-serializes the body before signature check, the signature won't match. We use express.raw() only on /webhooks/stripe — every other route still gets the normal JSON parser.

src/main.ts (excerpt)
app.use('/webhooks/stripe', express.raw({ type: '*/*' }));

14. Email delivery

We use Resend for transactional email. Templates live in src/common/email/<domain>/<name>.template.ts, each exporting a function that returns an HTML string.

The two paths

Path How Used for
Direct emailService.sendXxxEmail(...) Auth flows (verification, password reset), feedback confirmations, invoice override-email path. Synchronous, fire-and-forget.
Via the notification system notificationService.notify(...) → EmailSendWorker → Resend Anything that's also a bell notification (invoice paid, group invitation accepted, refund issued).

Template structure

All templates share a base layout (src/common/email/_layouts/base-layout.ts) which provides baseLayout, heading, paragraph, primaryButton helpers.
